# TestPlat 首期黄金验收流程

## 1. 文档状态与用途

- 状态：GF-01 至 GF-03 已于 2026-09-21 经用户确认；SQL 只读属于 P0 并新增 GF-04，实施优先级低于前三条流程；ES 不属于 P0。
- 本文从 `testplat-new` 当前资产和历史运行证据中选择三条真实业务流程，并新增一条独立 SQL 只读探针，按照 TestPlat 新平台已确认的领域边界重新表达。
- 旧项目只提供业务事实、风险和验收证据，不是新平台运行时依赖。旧 DSL 字段、隐式上下文、默认身份、路径身份和项目专属执行代码不得直接搬入新平台。
- 本文定义黄金流程的业务目标、边界和验收证据；可执行 YAML 的字段结构以已批准 DSL 文档为唯一权威。

## 2. 选择原则

前三条黄金业务流程必须共同证明：

1. API 业务流程能够通过显式契约、类型化输入输出和不可变步骤输出完成。
2. API 产生的业务标识能够显式传给隔离的 Browser 会话，并形成页面证据和清理结果。
3. 多目标系统、多被测身份、有限集合和不可逆业务动作能够在统一风险、失败和证据模型下执行。
4. 两个业务项目使用同一版本的通用 Engine 和 Worker；差异只存在于资产、平台配置、凭据引用及经批准的受控 Adapter。

SQL 只读验证是 P0 必验能力，但实施优先级低于前三条黄金业务流程。`testplat-new` 的提现场景提供了受控数据库步骤的现有结构，参考文档也已有连接和查询示例；不过现存提现运行在首个 API 404 后失败，SQL 步骤并未真实执行。因此 GF-04 只继承受控连接、静态语句和结果契约需求，不继承旧流程的隐式参数或“查询最新一条”等不确定语义。

## 3. GF-01：E3E3 多 SKU 余额支付

### 3.1 来源证据

- 参考资产：`testplat-new/assets/scenarios/e3e3/order/full_pay/multi_sku_payment_success.case.yaml`。
- 已有成功运行：`20260820T134217_case-e3e3-full_pay-order-items-multi_sku_payment_success`，结果为 `pass`。
- 该流程以一个有序多 SKU 列表创建单笔订单，再通过 API 完成余额支付；订单号、金额和支付结果能够被结构化记录。

### 3.2 新平台业务流程

1. Scenario 绑定一份只读 DataSet，取得多个商品的稳定业务选择条件、数量和配送数据。
2. 通过只读 ApiContract 广泛搜索候选商品，并使用受限 `$select` 按稳定商品编号精确选择；零匹配或多匹配必须失败，不得回退到第一条结果。
3. 通过多个具有显式输入输出的 Flow 计算或查询运费、服务费和订单预结算信息。公司业务费用以被测系统接口返回为准，通用内核不实现业务计费算法。
4. 使用采购方 API 身份创建一笔包含全部订单行的待支付订单，公开类型化的 `orderNo`、`orderItemIds` 和 `payableAmount`。
5. 只读查询账户余额，使用版本化 decimal 转换操作符校验余额足够支付。
6. 只执行一次余额支付动作。支付成功响应即使业务数据为 `null`，仍必须由 ApiContract 的成功语义和显式业务上下文形成支付结果。
7. 支付后只允许通过只读订单查询确认订单号和已支付状态；支付请求本身不得进入等待轮询、故障重试或自动重跑。

### 3.3 旧语义改造

- 删除 Case 级 `default_as`；每个 API Step 在自身声明 `auth.actorRef`。
- 将 `${...}`、任意日期函数和旧表达式分别改为 `$ref`、`$select`、`$template` 或版本化 `data.transform`。
- 将旧 Flow 的隐式上下文改为声明式输入、类型化根输出；Scenario 只能读取 Flow 的公开输出。
- 删除 Case 级 `retry_safe: false` 作为执行依据。不可逆支付 Step 默认没有重放授权；后续只读查询可以在明确 `replay.allowedFor: [wait]` 后轮询。

### 3.4 通过标准

- 订单包含 DataSet 声明的全部商品行，每一行都以稳定 ID 关联，不依赖返回顺序或重复 SKU 文本匹配。
- 报告可以还原商品选择、费用结果、订单请求、订单号、支付前余额、支付金额、支付响应和支付后只读确认。
- 任意支付结果不确定时 Run 失败并停止，平台不自动再次支付。
- 凭据、支付密码、Token 和 Cookie 不进入资产或普通日志；实际业务请求中的认证值可以进入加密 raw 证据，并且只能由具备相应权限的用户在线查看，所有查看必须审计，P0 不提供下载或导出。

## 4. GF-02：GO2 API 建单后 Browser 可见性验证与清理

### 4.1 来源证据

- 参考资产：`testplat-new/assets/scenarios/go2/order/full_pay/items_search_visible.case.yaml`。
- 已有成功运行：`20260904T152927_case-go2-order-full_pay-items_search_visible`，结果为 `pass`，完整执行 API 建单、Web 搜索、截图和取消订单。

### 4.2 新平台业务流程

1. 使用 API 通道的采购方身份创建一笔待支付多商品订单，公开类型化 `orderNo`。
2. 使用同一业务身份对应的 Web 认证 Profile 建立独立 Browser 会话；API Token 或请求头不得直接注入 BrowserContext。
3. 通过 PageContract 打开门户并进入订单系统，保存 `browser.open` 返回的运行时页面句柄。页面跳转或打开新标签页后，后续步骤显式传递动作返回的 `pageHandleRef`，并切换到目标页面的 `pageRef`。
4. 只读等待订单页搜索控件唯一可见，再填写本次 `orderNo` 并搜索。
5. 读取唯一订单行，断言页面展示的完整订单号与 API 输出一致，并保存截图制品。
6. 主验证完成后进入 cleanup，使用明确页面元素取消本次待支付订单并确认；cleanup 不得重放创建订单或其他主流程动作。

### 4.3 旧语义改造

- 删除依赖当前页面、最近标签页、最近元素或默认身份的隐式簿记；`browser.open` 以外的 Browser Step 显式声明 `pageRef`、`pageHandleRef` 和 `auth.actorRef`。
- 删除通用 `ui.dismiss`。黄金验收身份必须预先完成一次性引导；若业务弹窗是稳定流程的一部分，则必须在 PageContract 中声明明确元素并使用普通 `browser.click`。
- 旧 `wait_until` 改为只读 `browser.read` 的有界等待，并显式申请 `wait` 重放用途；点击、填写和订单取消不得因等待机制被重复执行。
- 取消订单移入 cleanup，并与主验证结果分别记录。cleanup 最终如何影响 Run 状态由后续运行判定决策统一冻结。

### 4.4 通过标准

- API 输出的 `orderNo` 只能通过显式 Step/Flow 输出进入 Browser Step，不存在全局变量或跨通道会话共享。
- API 与 Browser 使用独立认证状态，但能够解析为同一业务身份；切换通道不会泄漏 Token、Cookie 或 BrowserContext。
- GF-02 使用平台认证的 Playwright Chromium 构建运行，运行快照和报告记录实际浏览器构建标识。
- 搜索结果必须唯一命中完整订单号；零命中、多个候选或前缀误命中均失败。
- 报告包含页面跳转、控件等待、填写值的访问控制记录、读取结果、断言、截图和 cleanup 结果。

## 5. GF-03：E3E3 多 SKU 部分售后与整批退款

### 5.1 来源证据

- 参考资产：`testplat-new/assets/scenarios/e3e3/take_return/full_pay/multi_sku_refund.case.yaml`。
- 已有成功运行：`20260820T134739_case-e3e3-full_pay-take_return-items-multi_sku_refund`，结果为 `pass`。
- 该流程覆盖采购方、代发管理员、拿货员和退款管理员等多个业务身份，以及支付、拿货结算、售后、退件入库、退货结算和退款确认等高风险动作。

### 5.2 新平台业务流程

1. 复用 GF-01 的订单准备能力，创建并支付一笔包含多个商品行的订单。
2. 只读查询采购订单行和待拿货记录，以稳定 `orderItemId` 精确建立订单行到拿货行的关系；不得依赖列表顺序、商品名称或重复 SKU。
3. 使用有限 `collection.map` 按原顺序逐行调用已发布 Flow，准备拿货指派输入并聚合显式输出；任一项失败立即停止并记录失败索引。
4. 代发管理员完成批量指派，拿货员查询结算明细并执行一次整批拿货结算。
5. 采购方按 DataSet 中显式声明的部分售后数量创建售后；售后数量作为后续退件、退货结算和退款的上限，不允许下游步骤静默改写。
6. 代发管理员只读查询退件信息，再按稳定退货行 ID 完成入库和任务指派。
7. 拿货员查询退货结算明细并执行一次整批退货结算。
8. 退款管理员只读查询每条退货行的可退款金额和快递费，以被测系统返回值为权威，逐行核对后执行一次整批退款确认。
9. 最后仅通过只读 API，或为该业务单独定义并验收的 SQL 受控查询，验证订单、拿货、售后、退货和退款的最终状态及稳定 ID 关系。GF-04 的固定用户探针只验收 SQL 基础能力，不作为本流程的业务状态证据。

### 5.3 风险与重放边界

- 支付、拿货结算、退货结算和退款确认都是不可逆动作，默认无任何重放授权。
- 等待状态同步时，只能重复执行已经明确授权的只读查询；不得把前序写动作包进等待或集合重放。
- 每个写动作执行前必须冻结目标系统、身份和全部解析后输入；结果不确定时 Run 失败并停止，由人工依据只读证据判断真实业务状态。
- 后续人工再次发起属于新的 Run，不能继承上一次风险确认，也不能由平台因失败自动启动。

### 5.4 通过标准

- 报告能够还原 `orderItemId -> takeId -> returnListItemId` 的逐行关系，且在返回顺序变化或重复 SKU 情况下仍准确。
- 每个身份、目标系统和通道均显式可见；任何一个身份的凭据或会话不得被另一身份、目标或通道复用。
- 有限集合执行保持输入顺序、输出顺序、失败索引和已完成项证据。
- 退款金额、服务费和快递费来自被测系统权威接口或受控查询，不在通用内核中重新实现业务算法。
- 任一不可逆动作发生不确定结果后，后续不可逆动作均不得继续执行；报告保留最后一次已知响应和停止位置。

## 7. GF-04：测试环境固定用户的 SQL 只读验证

### 7.1 来源与改造理由

- `testplat-new/assets/scenarios/go2/withdraw/refuse_notify_pending.case.yaml` 已有 `db.main` 参数绑定查询，证明业务流程需要使用 API/身份上下文查询数据库状态。
- `testplat-new/docs/reference/connections.md` 已有订单表参数化查询示例。
- 现存提现运行在首个 API 404 后即失败，SQL 步骤没有真实执行，因此这些材料不是成功验收证据，只作为迁移需求来源。
- 本次 SQL 验收改为固定的单条只读探针，不依赖前置业务造数，也不把查询结果伪装成订单链路证据；它只验收受控连接、只读策略、静态 SQL 执行和结果契约。
- `刘高杰` 是用户在 E3E3 测试环境中长期使用的测试用户，生产环境不存在。该名称只允许出现在版本化验收资产和需求文档中，不得写入 Engine、Worker、Adapter 或其他通用代码。

### 7.2 新平台业务流程

1. 使用项目环境解析出的只读 `connectionRef`，执行下面这条固定 SQL；语句文本作为验收资产的一部分冻结，不接收运行时 SQL、用户输入或前置步骤参数：

   ```sql
   select id from db_go2.user where username = '刘高杰' and source = 'e3e3';
   ```

2. 查询设置 `maxRows: 2`，以便区分零行、恰好一行和多行；本用例不依赖返回顺序，也不使用“最新一条”语义。
3. 结果必须恰好返回一行，且该行的 `id` 存在并且非空；零行属于断言失败，多行属于数据歧义失败。
4. 这是单次只读执行，不增加等待轮询或业务写动作；运行报告记录 SQL 摘要、逻辑连接、返回行数、截断标记、耗时和断言结果。
5. 数据库使用只读账号、只读事务、单语句限制、SQL 能力校验和结果行数上限；YAML 不包含地址、用户名、密码或连接串。
6. 该验收 Scenario 只允许选择 `test` 环境；其他环境不得为其提供可运行的受控连接绑定，尤其不得通过名称相近的数据在生产环境替代执行。
7. `connectionRef` 必须解析为 P0 认证的 MySQL 只读连接；PostgreSQL 或 SQLite 的通过结果不能替代本验收。

### 7.3 通过标准

- SQL 语句与验收资产完全一致，不使用 `$template`、字符串拼接、动态表名或运行时替换；本用例没有参数绑定项。
- 查询结果恰好一行，`id` 非空，且 `result.meta.truncated` 为 `false`；不得以 `maxRows: 1` 隐藏重复数据。
- 报告记录逻辑连接、语句摘要、返回列、返回行数、截断标记、耗时和断言，不泄漏连接凭据或其他未授权业务列。
- 缺少连接绑定、只读策略或必要列权限时，在执行前或查询阶段以稳定的 `configuration` / `policy` 失败呈现，不允许降级到其他连接。

## 8. 接入时仍需验证的事实

GF-04 的逻辑 `connectionRef` 到实际只读连接的 `test` 环境绑定、只读账号权限和返回的 `id` 类型仍须在接入时验证；SQL 的表、列、条件和测试环境边界已经由本验收用例冻结。

## 9. AC-01：轻量审计闭环

P0 上线前必须用两个不同授权的平台用户完成以下验收：

1. 无 `view_audit` 能力的用户不能进入审计页面或通过接口查询审计事件；具备该能力的用户可按操作者、动作、对象、结果和时间范围查询。
2. 分别执行一次资产发布、权限变更、raw 查看、凭据揭示和项目归档恢复；每个操作均产生可以通过对象引用和请求追踪标识关联的审计事件，成功与失败结果均能区分。
3. 审计事件包含稳定 ID、操作者、UTC 发生时间、动作、对象类型与引用、结果、非敏感变更摘要和策略版本；Web 按 `Asia/Shanghai` 展示时间时不改变原始 UTC 时间点。
4. 使用特征值搜索审计存储和备份样本，确认其中不包含本次操作涉及的 Token、Cookie、密码、验证码、业务请求响应或连接凭据明文。
5. 任何平台用户都不能通过 Web 修改或手工删除单条审计事件；P0 界面不提供审计导出功能。
6. 分别断开审计写入能力后尝试 raw 查看、凭据揭示、权限变更和 Worker 凭据使用；真实值不得返回，配置变更不得提交，Worker 不得发起外部动作。审计查询自身失败只显示查询错误，不影响另一条正在运行的 Run。
7. 审计保留策略默认 365 天；设置为 89 天、731 天或永久保留均被拒绝，缩短到合法范围时展示影响范围并要求二次确认。

## 10. AC-02：受管通知渠道

1. 获权用户在测试项目下创建两个钉钉通知渠道，Webhook 与签名密钥加密保存且不出现在 API 返回、审计、日志或运行快照明文中。
2. 无 `manage_notification_channel` 的用户不能创建、修改、测试或停用渠道；手动运行和定时任务只能选择已有 `channelRef` 或稳定平台用户 ID，临时 Webhook、密钥、手机号和钉钉用户标识必须被拒绝。
3. 对 `passed`、`failed` 和 `rejected` 各触发一次通知，验证正确渠道收到状态、耗时、摘要和报告链接，且不含原始业务数据或凭据；模拟投递失败时，Run 结果不改变。

## 11. AC-03：项目归档与恢复

1. 归档一个存在启用定时任务和排队 Run 的项目，验证定时任务停用、排队 Run 以 `PROJECT_ARCHIVED` 拒绝，新同步、发布和运行被拒绝，历史证据继续按保留策略可查。
2. 恢复项目后，原定时任务仍为停用，已拒绝 Run 不重新入队，归档期间触发不补跑，且不自动同步 Git 或发布资产。
3. 用户显式启用一个定时任务或创建新 Run 后，恢复后的后续工作才开始；归档与恢复操作均可在审计中追溯。

## 12. AC-04：维护窗口升级

1. 进入维护模式后，新手动 Run、Git 同步、发布和配置变更均被拒绝，定时触发跳过且升级后不补跑。
2. 使用一个正在运行的 Run 验证升级不会强制终止其 Worker；维护窗口超时时升级中止而不改变该 Run 的执行语义。
3. 放入一个依赖旧 Adapter 版本的排队快照：新部署包兼容时升级后继续执行；不兼容时预检必须阻止升级。
4. 升级前备份通过可读性验证；模拟迁移失败时不启动新版本，并能通过恢复该备份回到升级前状态。

## 13. AC-05：定时任务项目所有权

1. 用户创建并启用定时任务后被管理员禁用，下一次合法触发仍由平台调度器创建 Run；事件包含任务版本、`createdBy` 和调度器身份，不记录为被禁用用户在线操作。
2. 被禁用用户不再收到站内通知，但任务选择的项目钉钉渠道继续工作；无权用户不能修改或重新启用任务。
3. 管理员可以按创建者检索并批量停用历史任务，全部操作形成审计事件。

## 14. AC-06：通知渠道版本与紧急停用

1. Run 冻结渠道版本后执行普通密钥轮换，该 Run 完成时仍按旧版本向原目标投递；新 Run 使用新版本，两个快照都不包含密钥明文。
2. 渠道紧急停用后，引用任一历史版本的待发送和重试通知停止并记录 `NOTIFICATION_CHANNEL_DISABLED`，不改发其他渠道且不改变 Run 结果。
3. 被历史快照引用的渠道不能永久删除；不存在待投递事件前，普通轮换所需旧密钥版本不得提前清除。

## 15. AC-07：平台主密钥与信封加密恢复

1. 使用不同数据密钥加密两份相同敏感值，确认密文不同，且数据库、普通配置、日志和制品中不包含平台主密钥。
2. 轮换平台主密钥后，新数据使用新版本，旧数据仍可通过对应旧版本解密；完成重加密或数据过期前不得删除旧版本。
3. 在隔离环境分别恢复数据备份与独立保管的主密钥副本，确认历史凭据和 raw 证据可解密；缺少或错配主密钥版本时平台启动失败且不生成替代密钥或改写密文。

## 16. AC-08：HTTP 到 HTTPS 的无迁移切换

1. 以 `internal_http` 启动时，平台仅通过受控内网地址访问，Cookie 至少包含 `HttpOnly` 和适当 `SameSite`，浏览器存储中不存在 Token、会话标识、密码或 raw 数据；部署检查必须拒绝已知公网监听或公网外部地址配置。
2. 在不修改数据库、业务资产和运行快照的前提下，为同一部署增加可信反向代理、域名和证书，切换到 `https_required`；登录、报告、通知链接、API 和 WebSocket 均使用 HTTPS/WSS，Cookie 同时包含 `Secure`。
3. 伪造来自非可信来源的 `X-Forwarded-Proto`、`X-Forwarded-Host` 或客户端地址请求头，不得改变平台判断的协议、外部链接或审计来源；可信代理转发时则按配置正确解析。
4. `https_required` 模式下直接 HTTP 请求只能被受信任入口重定向到 HTTPS 或明确拒绝，绝不能建立登录会话、返回 raw 数据或降级发送会话 Cookie。

## 17. AC-09：Web 会话与请求来源保护

1. 登录前后、重新认证前后和权限提升前后，会话标识均发生轮换且旧标识立即失效；浏览器 Cookie 为 `HttpOnly`，浏览器存储中不存在 JWT、Token 或会话标识。
2. 对运行触发、权限修改、raw 查看和凭据揭示分别发送缺少 CSRF Token、错误 Token、非受信任 Origin 和跨域携带凭据的请求，均不得产生操作或返回真实值。
3. 密码重置、账号禁用和“退出全部会话”后，既有会话在下一次请求立即失效；权限撤销无需等待会话过期即可生效。

## 18. AC-10：平台用户身份生命周期

1. 用户使用登录名、显示名称和符合规则的密码自助注册后立即成为 `active`，自动获得普通用户角色，可以浏览并运行平台内所有测试项目的已发布资产，但只能查看自己的 `masked` 结果；公共注册不能获得管理员或超管能力。`pending` 仅保留给未来受邀或管理员预创建账号。
2. 管理员升权、换角色或禁用用户后，权限按新角色即时生效；变为 `disabled` 后不能登录或接收站内通知，历史审计、任务和运行仍以原 `userId` 可查。
3. 同一 IP 在连续 10 分钟内前 10 次注册请求按正常规则处理，第 11 次被限流；同一规范化登录名前 5 次尝试按正常规则处理，第 6 次被限流。两类超限均返回相同提示且不暴露登录名是否存在，10 分钟窗口结束后恢复。弱密码被拒绝，成功注册、默认角色分配、限流命中和后续授权变化均形成不含密码的审计或安全事件。
4. 修改显示名称后，新审计显示新快照，历史审计保留原快照且二者关联同一 `userId`。
5. 修改登录名、永久删除用户或创建与历史登录名相同的新用户必须被拒绝；最后一个具备授权管理能力的账号仍受既有防锁死规则保护。

## 19. AC-11：Worker 注册与最小权限

1. 一次性注册 Token 成功使用一次或到期后不能再次注册 Worker；两个 Worker 获得不同服务身份与凭据，镜像和代码扫描中不存在共享全局 Token。
2. Worker 可以声明能力、领取自身任务、读取当前任务所需最小材料并上报事件/制品，但访问用户、角色、授权或普通配置管理接口均被拒绝并审计。
3. 轮换一个 Worker 凭据后旧凭据立即失效；禁用 Worker 后不再分配新任务，正在运行的 Run 按稳定平台失败规则结束且不自动重放。

## 20. AC-12：平台依赖与测试出站隔离

1. 浏览器可以通过 Control API 创建和查看受控业务数据库及认证 Redis 配置，但 API 返回和浏览器存储不包含连接凭据，浏览器不直接连接数据库或 Redis。
2. Control 以专用服务身份访问平台数据库和架构采用的 Redis/队列；Worker 以 Worker 服务身份访问调度与当前任务材料。将这些平台内部地址配置为普通 Target System、Managed Connection 或通知渠道时必须被统一出站策略拒绝。
3. 通过合法 Managed Connection 执行 GF-04 业务数据库查询，并通过认证专用 Redis 获取一次验证码，证明业务数据库和业务 Redis 未被笼统禁止；项目规则可以收紧但不能扩大部署策略。
4. 分别使用域名解析到禁止 IP、HTTP 重定向到禁止地址和云元数据地址进行测试，连接均在发送敏感请求前被拒绝并产生结构化策略记录。
5. 超管创建一个限定资源类型、地址、端口和有效期的例外后，仅匹配访问可以通过；过期、越界或其他项目访问仍被拒绝，例外创建、修改和使用均可审计。

## 21. AC-13：手动运行创建幂等

1. 使用同一用户、`invocationId` 和规范化调用内容并发提交两次，只创建一个 Run、一份快照和一个队列项，两次响应返回同一 Run ID。
2. 24 小时内用相同 `invocationId` 更改资产、环境或运行策略时返回幂等冲突且不创建 Run；使用新 ID 显式再次运行则创建新 Run。
3. 模拟浏览器响应超时后重试，确认不可逆业务动作只属于原 Run；前端按钮即使未禁用也不能绕过服务端幂等。

## 22. AC-14：配置并发冲突

1. 两个管理员读取同一目标系统版本并分别修改，第一个保存成功后，第二个以旧 `expectedVersion` 保存必须冲突且不得覆盖第一项修改。
2. 批量修改中任一实体版本冲突时全部不提交；冲突响应展示非敏感差异，但不包含凭据、Webhook 或旧密文对应明文。
3. 刷新并基于新版本重新提交后成功，成功和冲突尝试均可在审计中追溯。

## 23. AC-15：活动修订切换与回退

1. 发布新修订后，新 Run 使用新活动修订；此前形成快照的排队或运行中 Run 继续使用原修订。
2. 重新激活上一历史已发布修订后，新手动 Run 和新定时触发使用旧修订内容，既有 Run 不改变，也不自动重跑或补跑任何历史 Run。
3. 任意 SHA、未发布同步提交或缺少当前能力兼容性的历史修订不能被设为活动修订；失败切换不改变当前活动引用。

## 24. AC-16：高影响操作近期认证

1. 登录超过 15 分钟后，凭据揭示、授权修改、重置他人密码和创建 Worker 注册 Token 均要求当前用户重新输入平台密码；认证失败不执行目标操作。
2. 重新认证成功后轮换会话标识，15 分钟内可继续执行获权的上述操作且每次操作仍单独审计。
3. raw/revealable 查看、普通项目名称、通知接收人、定时任务和审计查询不弹出重新认证，但仍按当前能力和审计规则执行。

## 25. AC-17：轻量自动备份与恢复

1. 将每日自动备份时间配置为一个临近测试时点，确认只执行一次完整备份；修改执行时间后只影响下一次尚未开始的备份，不补跑旧时点，也不接受 Cron、每天多次或按项目备份配置。
2. 连续生成超过 7 天的测试备份后只保留最近 7 天；备份失败产生结构化运维事件并向超管发送站内通知，不把备份失败伪装成测试 Run 失败。
3. 部署管理员使用恢复命令将数据库、制品元数据、发布修订和独立保管的主密钥恢复到隔离环境，在 `RPO <= 24 小时`、`RTO <= 4 小时` 内读取历史运行，且未完成 Run 不会自动重放。

## 26. AC-18：运行数据只按保留策略清理

1. 普通用户、管理员和超管均找不到也不能调用手工删除单个 Run、报告、日志、请求响应、截图或制品的能力；归档项目后历史运行仍按当前权限可查。
2. 获权用户缩短保留期时必须先看到受影响范围并二次确认；只有已超过新期限的数据进入既定删除作业，清理结果形成不含业务明文的审计事件。
3. 延长保留期不能恢复已经清理的数据，项目恢复也不能恢复已经到期删除的运行事实。

## 27. AC-19：P0 不提供平台配置包迁移

1. Web 和平台 API 均不提供项目、环境、目标系统、受控连接、身份、角色权限或通知渠道的配置包导入导出入口。
2. 部署备份只能通过受控恢复命令整体恢复，不能选择性导入某个项目或绕过目标部署的主密钥、凭据和权限边界。
