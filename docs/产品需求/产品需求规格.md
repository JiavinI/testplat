# TestPlat 产品需求规格

## 1. 文档状态

- 状态：已确认的产品需求基线。
- 本文定义用户能力、产品边界、业务行为、优先级和验收要求；不作为 YAML 字段、Schema、操作符或执行语义的第二份权威规范。
- 最小 DSL 设计已于 2026-09-21 审核通过，批准版本见 [2026-09-21-最小领域专用语言设计.md](../设计/2026-09-21-最小领域专用语言设计.md)。
- 本文中的 YAML 字段、代码片段和语法描述仅用于解释产品约束；DSL 文档是字段语法的唯一权威来源。若二者发生冲突，必须先判断产品要求是否变化，再显式修订对应权威文档，不能静默选择其中一份实现。
- 控制面、执行内核和跨组件协议仍须以本文及已批准 DSL 为约束，另行设计与确认。
- P0 与“首期”含义相同，表示首期正式交付和验收的硬门槛；P1、P2 为后续阶段，不进入 P0 完成判定。协议中为后续阶段预留但在 P0 没有触发入口的状态或字段，必须明确标注为 P0 不可达或不可配置。

## 2. 产品目标与范围

TestPlat 是一个全新的、通用且可长期演进的测试执行平台。它不是旧平台改造，也不直接搬运旧 DSL、旧执行器或公司专属配置。

核心闭环如下：平台 Web 管理并发布版本化 YAML 测试资产；独立 Engine 将已发布资产编译为确定性执行计划；Worker 执行可组合的 API 与 Browser 流程；平台可靠保存运行、结果、制品、日志和趋势。

更换公司或项目时，应只替换测试资产、环境、凭据引用和受控 Adapter，不修改通用内核。

首期服务测试环境；产品模型从开始即支持多个环境，并为后续开发环境留出位置。

P0 采用单一组织内部私有部署模式，可以服务多个团队和测试项目，但不提供租户级隔离。测试项目在 P0 是资产、配置、运行、命名和后续配额的管理边界，不是独立租户，也不是完整的平台用户授权边界；多组织、多租户及按项目配置的细粒度授权属于后续阶段。

## 3. 基本原则

1. 平台用户、被测系统身份和凭据是三个独立概念，见 [领域术语.md](../领域模型/领域术语.md)。
2. Git 中的资产是首期唯一可写权威；平台只能读取、校验、发布和运行已发布版本。
3. 发布修订和运行快照必须不可变，运行不得读取随后变化的分支、资产或配置。
4. 跨目标系统只能显式传递业务数据；不得隐式共享 Cookie、Token、BrowserContext、认证状态或凭据。
5. 业务写操作、支付、结算、退款及其他不可逆动作默认不得因不确定结果而自动重放。
6. 平台通用内核不得包含公司项目名、站点地址、登录页面规则、业务字段或业务资产。

## 4. 领域与配置边界

### 4.1 平台配置实体

以下内容由平台 Web 管理，不属于 YAML 测试资产：

- 测试项目：资产、目标系统、受控连接、环境和运行的管理容器。
- 目标系统：一个项目下可被 Scenario 通过 API 或 Browser 调用的逻辑业务应用或服务，通过 `targetRef` 引用。
- 受控连接：一个项目下可被 SQL/ES 动作访问的数据库或检索连接，通过 `connectionRef` 引用，包含连接凭据引用与访问策略。
- 环境：用户一次选择的项目级运行上下文，首期重点支持 `test`，后续支持 `dev`。环境分别将 `targetRef` 解析为 API/Web 部署绑定，将 `connectionRef` 解析为 SQL/ES 连接绑定。
- 凭据、被测系统身份和认证 Profile。
- Git 资产源及其资产根目录、默认分支、同步记录和已发布修订。
- 项目通知渠道、定时任务、队列策略、通知策略、运行记录、报告、制品和保留策略。

所有可修改的平台配置实体必须具有不可变版本号。Web 更新时提交读取时的 `expectedVersion`；当前版本不一致时返回结构化版本冲突，禁止静默采用最后写入者覆盖。页面应展示当前版本与用户编辑版本的非敏感差异，用户刷新或合并后重新提交。凭据、Webhook 等不可重新显示的字段只展示是否已配置和版本引用，冲突响应不得返回旧明文；批量修改必须在全部版本检查通过后原子提交，不能部分保存。成功修改和版本冲突均需审计。

测试项目在 P0 只有启用与归档两种管理状态，不提供 Web 永久删除。归档后禁止新的 Git 同步、资产发布、手动运行和定时触发，已有定时任务自动停用；仍在排队的 Run 以 `rejected + policy / PROJECT_ARCHIVED` 结束。已存在的修订、运行、报告和制品继续按各自保留策略保存及删除，管理员可以恢复归档项目。恢复只重新允许后续同步、发布和创建新 Run；定时任务继续保持停用并须逐个显式启用，已因归档拒绝的 Run 不恢复或重新入队，不自动 Git 同步、发布或补跑归档期间触发。

目标系统与受控连接是测试项目下的并列配置实体，不是包含关系或继承关系。一个测试项目必须能够配置多个目标系统和多个受控连接；一个 Scenario 可以按步骤顺序跨多个目标系统，并组合访问多个受控连接。

平台自身系统依赖不是 Target System 或 Managed Connection。浏览器前端只访问 Control API；Control 可以使用专用服务凭据访问平台数据库以及架构采用的 Redis、队列和对象存储；Worker 可以通过自身服务身份访问调度、快照和制品所需的平台服务。上述访问属于平台组件依赖通道，不向 YAML、Scenario 或人工测试工具暴露。

测试执行出站通道用于访问被测业务系统：API/Browser 通过环境解析后的 Target System，`sql.query` 通过受控业务数据库连接，认证 Adapter 可以通过认证专用 Redis 连接获取验证码。用户可以在 Web 中管理这些配置，但浏览器不直接获得连接凭据或连接数据库/Redis；后续人工 SQL 工具也必须经 Control 授权和受控 Worker 执行。

用户发起一次运行时只选择一个环境，例如 `test`，不逐项选择目标系统或连接的部署。所选环境缺少场景所需的任一目标系统或受控连接绑定时，请求必须在进入执行队列前以 `rejected + configuration` 拒绝。P0 不允许用户临时拼接 API、Web、SQL 或 ES 的跨环境组合；确有需要时应创建具有明确名称和完整绑定的新环境。

### 4.2 YAML 测试资产

首期保留以下七类概念资产。它们是新 DSL 的设计边界，不代表照搬旧文件格式。

| 资产类型 | 是否可直接运行 | 职责 |
| --- | --- | --- |
| `ApiContract` | 否 | 定义一个 API 的请求、响应成功语义和逻辑目标系统绑定。 |
| `PageContract` | 否 | 定义一个 Web 页面、稳定元素定位和逻辑目标系统绑定。 |
| `DataSet` | 否 | 提供可复用的固定业务测试数据；不包含环境配置或凭据。一次性数据可以直接放在 Scenario 或 Step 内。 |
| `Flow` | 否 | 复用步骤序列，必须声明输入与输出。 |
| `Scenario` | 是 | 新平台唯一的业务流程执行单元，承接旧 `Case` 职责；P0 可组合 API、Browser、SQL 只读查询和受控数据转换，ES 只读检索属于后续扩展。 |
| `Suite` | 是 | 显式、有序的 Scenario 列表。 |
| `ApiCheckSet` | 是 | 一个 API 的命名校验变体集合，每个变体产生独立、可追踪结果。 |

所有首期 YAML 资产使用统一公共外壳：根级 `apiVersion` 声明 DSL Schema 版本，`kind` 声明资产类型，`metadata` 保存稳定身份和展示信息，`spec` 保存当前类型的严格业务定义。

```yaml
apiVersion: testplat.io/v1
kind: Scenario

metadata:
  id: order.createAndPay
  name: 创建并支付订单
  description: 创建订单并完成支付，验证主要业务链路
  tags:
    - smoke
    - order

spec: {}
```

- `apiVersion` 表示 DSL Schema 版本，不表示资产业务修订；资产修订由 Git 提交、已发布修订和内容摘要确定。首期正式发布使用 `testplat.io/v1`，后续不兼容语义必须使用新的 API 版本，不能静默改变 `v1`。
- `kind` 必须是当前 API 版本支持的资产类型。`spec` 由该 `kind` 的版本化 Schema 严格校验。
- `metadata.id` 必填，是同一测试项目内跨资产类型全局唯一的稳定语义 ID。ID 使用受限 ASCII 标识符；具体格式允许小写字母、数字以及分段用的点、下划线和连字符，并必须以小写字母开头。
- `metadata.name` 必填，是可修改的展示名称，不参与引用和身份判定。`metadata.description` 与 `metadata.tags` 可选；标签只用于搜索和辅助筛选，不能动态决定 Suite 正式成员。
- 文件路径只负责组织，移动或重命名文件不得改变资产身份。所有资产引用使用稳定 ID，不使用相对文件路径充当身份。
- 未知根字段、未知 `metadata` 字段和未知 `spec` 字段必须在发布前拒绝，不得静默忽略。
- 首期每个 YAML 文件只包含一个资产，不支持 YAML 多文档文件。
- 环境地址、密码、Token、Cookie、连接串和其他凭据不得出现在公共外壳或资产 `spec` 中。

`Suite` 不能以标签、路径或当前目录动态决定正式成员。标签可以用于搜索和辅助选择，但发布后的 Suite、定时任务和运行快照必须记录确定的成员及顺序。失败立即停止或继续执行由任务/手动运行配置决定，并写入运行快照，不作为 Suite 固定业务语义。

`ApiCheckSet` 的每个命名变体必须作为一级结果保存，不能只在运行时匿名展开为临时 Scenario。P0 同时支持正向变体和预期业务失败的负向变体；它服务于单接口 Web 运行、报告趋势和后续由接口文档生成草稿。

`ApiCheckSet` 的执行身份在 `spec.auth` 统一声明，同一集合内的所有变体共享该身份；不能让不同变体隐式继承平台默认账号，也不能在变体之间静默切换身份。API/Browser 校验必须在该处二选一声明 `auth.actorRef` 或 `auth.mode: anonymous`，与普通 Step 的认证规则一致。需要不同身份或不同认证语义时，应创建独立的 `ApiCheckSet`，使每个变体的结果、趋势和审计边界清晰。

新平台不并行保留 `Case` 与 `Scenario` 两种业务流程资产。旧 DSL 中 `Case` 的实际职责是完整业务链路编排，因此统一命名为 `Scenario`；迁移或参考旧资产时，`Case` 只作为历史语义映射，不作为新 DSL 类型。

### 4.3 测试数据的使用范围

测试数据采用混合模型，不强制每份数据都拆成独立 `DataSet`：

- 多个 Scenario 复用、数据量较大或需要环境覆盖的数据，使用 `DataSet`。
- 只在一个 Scenario 内共享的数据，使用 Scenario 局部变量。
- 只使用一次且规模较小的数据，可以直接写在 Step 的输入中。
- 前置步骤生成的数据，必须通过显式输出引用传递给后续步骤。

数据来源必须显式引用，不依赖全局隐式变量或不透明的深度合并。任何数据作用域都不得保存密码、Token、Cookie、连接串或其他认证机密；这些内容只能通过平台凭据和受控连接引用获得。

运行时动态取值首期只提供显式的 `$ref`、`$select` 和 `$template` 三种节点：`$ref` 读取已存在的确定地址，`$select` 在一份复杂数据内执行过滤、通配符、可选匹配或多结果查询，`$template` 将显式输入渲染为字符串。固定值继续使用普通 YAML 字面量；计算、集合加工和对象重组必须使用 `data.transform`，不得引入任意表达式或脚本求值。

固定且唯一的地址必须优先使用 `$ref`，例如 `$ref: result.body.data.orderNo`。只有需要查询语义时才使用 `$select`；`$select.from` 必须是显式值节点，不能把 `result.body` 等普通字符串隐式解释为引用。`$literal` 仅作为转义节点，使包含 `$ref`、`$select`、`$template` 等业务字段的对象按原始数据传递，不属于新的动态取值能力。

首期 `$ref` 只开放五个保留根：`datasets`（Scenario 或 ApiCheckSet 已绑定的数据集）、`vars`（Scenario 局部变量）、`inputs`（当前可调用资产的显式输入，包括 Flow 和 ApiContract）、`steps`（当前作用域中此前步骤的显式输出）和 `result`（当前步骤的标准动作结果）。不得开放 `global`、环境配置、凭据、Token、Cookie、连接信息或任意进程变量等通用读取入口。

`result` 只能在当前步骤的输出、断言和等待条件中使用；`steps` 只能引用当前步骤之前且在当前作用域可见的步骤。Scenario 不得穿透读取 Flow 内部步骤，只能读取 `flow.call` 的公开输出；Flow 不得直接引用调用方的 `datasets`、`vars` 或其他上下文，必须通过 `inputs` 接收。有限集合执行提供的当前项和索引也必须映射为被调用 Flow 的 `inputs.item`、`inputs.index`，不新增隐式根。cleanup 可以引用此前已成功产生且仍在作用域内的主步骤输出。

所有根名称均为版本化保留字。未知根、越权作用域、后向步骤引用、不存在的数据集别名、变量、Flow 输入或步骤输出，必须尽可能在发布前拒绝；只能在运行时确定的缺失值必须产生结构化 `data` 类失败，不能隐式转为空值。

`$ref` 使用受限路径语法：以保留根开头，普通对象字段使用点号，特殊字段名使用 `['field.name']` 或 `["field.name"]`，固定数组下标使用 `[0]`。首期不支持通配符、条件过滤、数组切片、动态下标、函数调用、计算或默认值。通配符、过滤和多结果查询统一使用 `$select`；数据计算和重组统一使用 `data.transform`。

`$ref` 表示确定地址必须存在。步骤 ID、输出名称和其他可静态解析的路径错误必须在发布前拒绝；响应内容中运行时才可确定的字段缺失，必须以 `data / REF_NOT_FOUND` 失败，不得静默转换为空值。允许缺失的数据必须显式使用 `$select` 的可选匹配语义。

`$select` 必须显式声明结果数量约束 `expect`，首期只允许 `one`、`optional`、`many`，不提供默认值。`one` 必须恰好命中一项，零项以 `data / SELECT_NOT_FOUND` 失败，多项以 `data / SELECT_AMBIGUOUS` 失败；`optional` 允许零项或一项，零项返回 `null`，多项仍以 `SELECT_AMBIGUOUS` 失败；`many` 允许任意数量并始终按源数据顺序返回数组，零项返回 `[]`，单项也返回单元素数组。

`$select` 保持选中值的原始数据类型，不执行隐式字符串或数字转换。执行时间线必须记录查询路径、数量约束和实际匹配数；最终值按运行的报告访问模式记录。首期不提供 `first`、`last`、`any` 等会隐藏零项或多项歧义的模式，也不得由查询操作修改源数据。

`$select.path` 必须是发布时可解析的静态查询字符串，不允许使用 `$template` 或其他字符串插值。运行时筛选值通过当前 `$select` 的 `params` 显式绑定，并在路径中以 `$params.<name>` 引用；参数值可以来自合法值节点，必须保持原始类型并作为完整数据绑定，不能改变查询结构或注入操作符。

`$params` 仅是当前 `$select.path` 的查询局部命名空间，不属于 `$ref` 根作用域，查询结束后立即失效，也不能通过 `$ref: params.*` 读取。路径引用的每个参数必须在同一 `$select.params` 中唯一声明；未声明、重复或声明后未使用的参数必须在发布前拒绝。

`$select.path` 首期采用 TestPlat 自身版本化的受限 JSONPath 子集，而不是把某个解析库的全部能力直接暴露为 DSL。首期支持根 `$`、普通与特殊字段、固定数组下标、数组或对象通配符、条件过滤、当前候选项 `@` 和局部查询参数 `$params.<name>`；过滤条件支持 `==`、`!=`、`>`、`>=`、`<`、`<=`、`&&`、`||`、`!` 和括号分组。

首期查询子集不支持递归下降、数组切片、正则、函数调用、算术、脚本表达式或动态生成查询路径。字段缺失表示当前候选项不匹配，最终是否失败由 `expect` 决定；相等比较不做字符串与数字的隐式转换，顺序比较遇到不兼容类型时以 `data / SELECT_TYPE_MISMATCH` 失败。查询结果必须保持源数据顺序。

查询子集及语义随 DSL 版本冻结。底层查询库只属于实现细节，依赖升级不得静默改变已发布资产的解析或匹配结果；Worker 不支持相应查询版本时必须在执行前拒绝。

`$template` 必须由静态模板字符串和局部 `with` 绑定组成，使用 `{name}` 引用当前模板参数，结果始终为字符串。参数名只允许 ASCII 字母、数字和下划线且不能以数字开头；同一参数可以重复使用，但模板中的每个参数必须唯一声明，未声明参数和声明后未使用的参数必须在发布前拒绝。

模板参数可以是普通字面量或合法值节点。字符串原样插入，整数和 decimal 使用稳定十进制文本，布尔值固定输出 `true` 或 `false`；`null`、对象和数组不得隐式字符串化，必须以结构化 `data` 类错误拒绝。需要保留非字符串类型时必须直接使用 `$ref` 或 `$select`，不得用只包含一个占位符的模板伪装类型传递。

模板中的字面花括号使用 `{{` 和 `}}` 转义。首期不支持条件、循环、默认值、过滤器、函数、格式表达式、对象序列化或嵌套模板。`$template` 只负责确定性字符串拼接，不承担 SQL、URL、JSON、Shell 或其他协议转义；相应协议必须使用结构化字段或参数绑定。

`$literal` 是递归关闭值节点解析的转义包装，不属于动态取值能力。求值时仅移除最外层 `$literal`，其内部完整子树按原始 YAML 类型和值传递；其中出现的 `$ref`、`$select`、`$template` 或 `$literal` 键均不得执行。需要同时包含原始保留字段和动态值时，必须把 `$literal` 缩小到纯静态子树，在外层通过独立值节点组合。

值节点只有在映射严格符合对应操作符结构时才可识别。包含 `$ref`、`$select`、`$template` 或 `$literal` 保留键但又带有不属于该节点的额外字段时，必须在发布前拒绝，不得猜测为值节点或普通业务对象；确属业务原始数据时必须显式使用 `$literal`。

`DataSet` 的共享范围是单个测试项目及其已发布修订。一个 Scenario 可以组合引用多份 `DataSet`，下单、拿货等不同业务流程可以引用同一份公共商品、收件人或配送数据；首期不支持跨测试项目直接引用，也不支持 `DataSet` 之间的继承、隐式覆盖或递归引用。

只有 Scenario 和 `ApiCheckSet` 可以直接绑定 `DataSet`。Flow 必须通过声明的输入接收所需数据，避免隐藏依赖并保持跨项目复用；ApiContract、PageContract 和 Suite 不得直接读取 `DataSet`。

`DataSet` 是只读的运行前输入。步骤产生的订单号、状态、查询结果等动态数据属于本次运行上下文，不得写回或修改 `DataSet`；后续步骤只能通过显式步骤输出引用这些数据。

### 4.4 ApiContract 请求契约

`ApiContract` 采用规范化的 HTTP 请求槽位，不沿用旧平台 `json`、`query`、`form` 三选一的结构。契约必须通过 `targetRef` 绑定逻辑目标系统，并在 `request` 中声明方法、相对路径和业务输入；可选的路径参数、查询参数、业务请求头和请求体可以同时存在。

- `targetRef` 只引用平台中的逻辑目标系统；真实协议、域名和端口由环境绑定提供，资产不得包含绝对 URL。
- `request.method` 首期支持 `GET`、`POST`、`PUT`、`PATCH`、`DELETE`、`HEAD` 和 `OPTIONS`；`request.path` 必须是以 `/` 开头且不包含 scheme、host 或 query 的相对路径。
- `request.inputs` 声明调用者可传入的业务参数，并至少能够表达名称、类型、是否必填和说明。契约内部通过 `$ref: inputs.*` 将这些输入映射到 HTTP 报文；调用者不得传入未声明参数，必填值缺失必须在发起网络请求前失败。
- `request.pathParams` 只为路径占位符绑定值并执行标准 URL 编码；占位符、声明和绑定必须一一对应。禁止使用 `$template` 直接拼接路径来绕过编码或静态校验。
- `request.query`、`request.headers` 和 `request.body` 是相互独立且可同时存在的结构化映射，不得用一个互斥的 `request.type` 决定整份请求。
- `request.body` 通过 `mediaType + value` 表达。首期支持 `application/json` 和 `application/x-www-form-urlencoded`；multipart、文件和二进制作为后续版本化能力扩展。
- `Content-Type` 由 `body.mediaType` 产生。`Authorization`、`Cookie`、`Proxy-Authorization` 等认证或会话请求头不得写入资产，由认证 Profile 注入；普通业务请求头必须在 Contract 中声明和映射，调用 Step 不得绕过 Contract 任意追加。
- ApiContract 不得包含环境地址、凭据、被测系统账号、具体 `actorRef` 或固定测试数据。执行身份由调用 Step 显式声明，再按环境、目标系统和 API 通道解析认证 Profile。
- 只有已确认无业务副作用的只读 ApiContract 才能在 `spec.replay.allowedFor` 中声明 `authRefresh`，表示认证刷新后重放的契约上限。创建、修改、支付、结算、退款及其他业务写入 Contract 不得声明该用途；发布校验不能仅凭 HTTP 方法推断安全性。
- 平台不能从 HTTP 方法静态证明业务无副作用。声明 `authRefresh` 是 Contract 作者作出的可审阅安全承诺，由拥有 `publish_asset` 的发布者在发布整个修订时确认；平台保存声明变更、发布者、修订和 Step 使用理由的审计证据，不增加专门审批流，也不把 GET 或 POST 自动等同于安全或不安全。

旧平台已验证的“业务输入到真实 HTTP wire 报文集中映射”能力应保留；旧 DSL 的 `host`、`request.type`、Step 任意 headers 和 `${...}` 模板语法不作为新契约直接继承。

### 4.5 ApiContract 响应成功语义

`response.success` 必须把 HTTP 状态接受规则与业务成功断言分开声明。`status` 为必填数组，可包含精确整数状态码或标准状态类别字符串，例如 `200`、`201`、`"2xx"`；业务 `assertions` 可为空，但存在时必须全部按声明顺序通过。

- 每条业务成功断言必须拥有当前 Contract 内稳定且唯一的 `id`，并复用版本化断言操作符和值节点；实际值、期望值和结果必须分别进入结构化时间线与报告。
- 标准 HTTP 动作结果至少提供 `result.status`、`result.headers`、`result.body` 和 `result.meta.durationMs`。响应头名称统一规范化为小写；响应体保持解析后的数据类型，不进行字符串与数字的隐式转换。
- 未收到 HTTP 响应的 DNS、连接、TLS 或网络协议错误归类为 `transport`，不执行成功规则。收到响应后先检查状态接受规则，再执行全部业务成功断言。
- 状态不被接受或任一业务成功断言失败时，Step 记录为 `failed + assertion`，并使用稳定错误码区分状态拒绝与具体 Contract 断言失败；HTTP 4xx/5xx 本身不得误记为传输失败。
- Contract 成功规则默认先于 Scenario 的步骤级断言执行。步骤级断言只能补充本场景要求，不得替换、关闭或静默放宽 Contract 成功规则。
- ApiCheckSet 的负向变体在 P0 可以显式声明预期 Contract 失败，但必须同时断言预期 HTTP 状态和至少一项稳定业务错误；两者全部满足时该变体通过。认证、传输、超时、动作执行或平台异常不能算作预期业务失败。该能力只属于 ApiCheckSet，通用 Scenario Step 不提供忽略 Contract 成功规则的开关。

首期不支持在 `response.success` 中配置任意脚本、隐式类型转换或无稳定 ID 的匿名断言。

`response.body.decodeAs` 必须由 ApiContract 显式声明，首期支持 `json`、`text`、`binary` 和 `none`，不得仅依据运行时 `Content-Type` 自动猜测或降级。`json` 将响应解析为对应 JSON 原生类型，解析失败记录为 `action / RESPONSE_DECODE_FAILED`；`text` 优先使用响应声明字符集，未声明时使用 UTF-8，非法字节不得静默替换。

`binary` 不把原始字节放入普通数据上下文，而将内容写入受访问控制的制品存储，并使 `result.body` 返回至少包含 `artifactRef`、`mediaType`、`size` 和 `sha256` 的描述对象。`none` 使 `result.body` 固定为 `null`，用于 204、HEAD 等不消费响应体的接口；实际非空内容仍进入受控原始响应记录。

`result.headers` 的名称统一规范化为小写，值始终为数组，以保留重复响应头。原始响应与解析结果均按报告访问模式保存；普通日志和默认报告遮罩认证值，具备 `view_raw_run_data` 能力的用户可以在受审计的 raw 视图中查看实际响应包含的 Token、Cookie、认证响应头和其他真实业务值。

### 4.6 PageContract 元素定位契约

`PageContract.elements` 使用结构化定位器定义稳定元素，不直接暴露任意选择器表达式。一个元素可以包含可选的 `frames`、可选的 `within` 和必填的 `locator`：`frames` 声明从主页面进入的 iframe 链，`within` 声明页面或当前 frame 内逐层缩小的容器链，`locator` 声明最终目标元素。三部分均按数组或声明顺序从外到内解析。

每个 `PageContract` 必须通过 `spec.targetRef` 绑定一个逻辑目标系统。页面入口 `spec.route` 可选：能够直接导航的页面声明 `route`；只能通过点击、重定向、弹窗、新标签页或第三方流程到达的动态页面可以不声明 `route`，但仍可定义稳定元素。

`route` 使用结构化的 `path`、`inputs`、`pathParams` 和 `query` 描述页面入口。`path` 必须是当前目标系统内的相对路径，禁止绝对 URL；`inputs` 声明调用者可传入的页面入口参数；`pathParams` 必须与路径占位符一一对应并进行标准 URL 编码；`query` 以结构化映射生成查询参数。页面资产不得声明请求头、认证信息或被测系统账号。

所有 Browser Step 都必须显式声明 `pageRef`，不得依赖当前会话中“最近一次打开的页面”等隐式簿记推断页面契约。`browser.open` 只能引用已声明 `route` 的 PageContract，并将显式调用输入映射到该 `route`；其他 Browser 动作可以引用无 `route` 的动态页面。引用 `pageRef` 只表示本步骤使用哪份页面和元素契约，不会自动导航，也不等于断言浏览器当前 URL。

运行时页面实例使用 `pageHandleRef` 显式传递。`browser.open` 创建页面并在 `result.page.handleRef` 返回仅对当前 Run 有效的句柄；其他 Browser 动作必须同时提供静态 `pageRef` 与动态 `pageHandleRef`。句柄必须通过当前或前序步骤的类型化输出传递，不允许使用“当前页”“最后打开页”或标签页序号。句柄不属于资产身份，不能跨 Run、目标系统、执行身份或 BrowserContext 使用。

点击、重定向或新标签页进入另一逻辑页面后，下一步必须显式改用目标页面的 `pageRef`，并使用动作返回的页面句柄。点击未创建新页面时 `result.page.handleRef` 保持原句柄；恰好创建一个新页面时返回新句柄；一次动作创建多个新页面时 P0 以结构化歧义失败结束，不猜测目标页。

首期定位方式只支持 `role`、`label`、`text`、`testId` 和 `css`。语义定位优先用于业务可见且稳定的元素；`css` 用于没有可靠语义标识的容器、iframe 或元素，并只接受固定 Playwright/Chromium 构建交给浏览器执行的标准 CSS 选择器。`css` 不接受 Playwright 文本引擎、XPath 前缀、`>>` 组合语法或其他私有扩展。`role` 至少可以声明角色、可访问名称和是否精确匹配；各定位方式的字段组合必须由 DSL Schema 明确定义并在发布前校验。

每一层定位默认且强制要求唯一匹配：零个元素以结构化 Browser 定位失败结束，多个元素以歧义失败结束。首期不提供自动取第一个元素、按页面状态尝试多个候选定位器或失败后回退定位器的能力，也不支持 XPath、JavaScript 定位和 Playwright 私有选择器语法。后续确有 XPath 需求时，应通过新 DSL 版本增加独立的 `xpath` 定位策略、语法约束和验收用例，不能把 XPath 字符串塞入既有 `css` 字段或静默改变 v1 语义。

元素定位结构示例如下：

```yaml
elements:
  firstRowPay:
    within:
      - by: css
        value: .order-table tbody tr:first-child
    locator:
      by: role
      role: button
      name: 立即支付
      exact: true

  paymentPassword:
    frames:
      - by: css
        value: 'iframe[src*="/open/gateway"]'
    locator:
      by: css
      value: '#password'
```

### 4.7 Browser Step 动作与结果契约

P0 只认证 Playwright Chromium，默认以无头模式运行；Firefox、WebKit、系统已安装 Chrome 和多浏览器兼容性矩阵不属于 P0。Worker 使用的平台浏览器构建标识必须进入能力声明和运行快照，不支持快照所需构建时在执行前拒绝。

首期 Browser Step 只支持 `browser.open`、`browser.click`、`browser.fill`、`browser.read` 和 `browser.screenshot` 五个动作。所有动作均遵守 PageContract 的显式 `pageRef`、步骤级 `auth.actorRef`、结构化元素引用和严格唯一定位规则。

- `browser.open` 接收 `pageRef` 和该页面 `route` 声明的显式输入，导航后返回新页面句柄；引用无 `route` 的页面必须在发布前拒绝。
- `browser.click` 接收 `pageRef`、`pageHandleRef` 和 `elementRef`，返回点击完成后应继续操作的页面句柄。
- `browser.fill` 接收 `pageRef`、`pageHandleRef`、`elementRef` 和 `value`，语义固定为清空现有内容后填写完整值，不模拟逐键输入。结果不重复回显填写值；解析后的输入按统一运行日志访问规则记录。
- `browser.read` 接收 `pageRef`、`pageHandleRef` 和 `elementRef`，返回公共页面结果及元素的 `text`、`value`、`visible`、`enabled`。隐藏但存在的唯一元素可以返回 `visible: false`；零匹配仍是定位失败，不得伪造一个不可见元素结果。
- `browser.screenshot` 接收 `pageRef` 和 `pageHandleRef`，对指定页面实例截图并返回受控制品描述。YAML 不得指定或取得 Worker 本地文件路径。

Browser 动作结果使用稳定的分区结构：`result.page` 至少包含动作完成后页面的 `handleRef`、`url` 和 `title`；`browser.read` 额外返回 `result.element`；`browser.screenshot` 额外返回 `result.artifact`，其中至少包含 `artifactRef`、`mediaType`、`size` 和 `sha256`。不存在的动作专属分区不得用空对象伪造。

任一 Browser 动作失败时，Engine 必须尽力保存失败截图并将其作为失败制品关联到该步骤；截图失败只能作为附加诊断记录，不能覆盖原始失败类别、错误码和原因。

首期不提供 `browser.login`、`browser.close` 或通用自动关闭弹窗动作。登录和会话建立由认证 Profile 管理，会话销毁由 Engine 生命周期管理；已知业务弹窗通过 PageContract 中的明确元素和 `browser.click` 处理。后续新增 Browser 动作必须通过版本化动作注册表、输入 Schema 和结果 Schema 扩展，不能改变既有动作语义。

### 4.8 SQL 只读动作与结果契约

P0 仅将 SQL 作为 Scenario 或 Flow 内的受控查询动作，不增加 `SqlContract` 资产。一次性查询可以直接写在步骤中；需要复用时，先封装为具有显式输入与输出的 Flow。只读 `SqlContract` 是否增加应依据后续真实复用和治理需求评估，不能仅因为 API 存在 Contract 就机械复制资产类型；但未来业务流程写库必须先引入受发布治理的 `SqlContract`，不得直接放宽内联查询步骤来执行写操作。

P0 产品受控连接只认证 MySQL，并以 GF-04 的真实 MySQL 连接作为正式验收。PostgreSQL 通过数据库 Adapter 协议保留后续扩展位置；SQLite 只可用于实现层单元或集成测试，不作为平台可配置的产品连接，也不构成 P0 验收证据。

`sql.query` 必须显式声明平台受控的逻辑 `connectionRef`、单条静态 `statement`、类型保持的 `params` 和受平台上限约束的 `maxRows`。SQL 文本不得使用 `$template` 或其他字符串插值；动态业务值只能通过参数绑定传入。首期只允许只读查询，并同时依靠只读数据库账号、只读事务、单语句限制和 SQL 语法/能力校验实施纵深防护，禁止仅以 SQL 是否以 `SELECT` 开头作为安全判断。

`sql.query` 返回 `result.rows` 和 `result.meta`。`rows` 是保持查询顺序的行对象数组；`meta` 至少包含 `columns`、`returned`、`truncated` 和 `durationMs`。结果达到平台或步骤上限时必须明确标记 `truncated: true`，不得让调用者把截断结果误认为完整集合。

SQL 查询使用受控连接自身的凭据，不使用被测系统身份的 `auth.actorRef`。首期不自动分页或无限拉取数据；后续步骤通过 `$ref`、`$select` 或步骤显式输出消费查询结果。等待数据库状态时继续使用统一等待与重放资格模型，不新增隐藏轮询。

ES 不属于 P0。后续引入 `es.search` 时，必须通过新的版本化动作能力明确声明 `connectionRef`、`indexRef`、结构化查询、排序和有界结果，不得把任意 HTTP、脚本、更新、删除或建索引能力伪装成只读检索，也不得静默改变 P0 DSL 的语义。

### 4.9 数据库能力扩展边界

数据库能力必须从首期开始区分三个上层入口：自动化流程只读查询、后续人工 SQL 测试工具、后续自动化流程写操作。三者可以复用同一套数据库 Adapter、受控连接解析、参数绑定、类型归一、超时、结果、日志和审计基础能力，但必须使用各自独立的触发、权限和风险策略，不能以一个无限制的通用 SQL 动作替代。

P0 只注册 `sql.query` 能力。数据库 Adapter 和动作注册协议必须显式声明所支持的操作类别与协议版本；不支持后续操作类型的 Worker 必须在执行前拒绝。未来新增 `sql.execute` 时不得改变 `sql.query` 的只读语义或结果契约。

后续 SQL 测试工具面向获权平台用户，可以允许临时填写 SQL，并按查询、预览、确认执行、权限和审计策略受控运行；它不属于版本化 Scenario，不得自动获得定时运行或重放资格。后续自动化流程写操作只能引用已发布且不可变的 `SqlContract`，不得在 Scenario 或 Flow 中内联任意写 SQL。

只读查询和写操作必须使用能力及凭据隔离的受控连接。写操作至少需要显式操作类别、允许的语句能力、参数 Schema、事务策略、预期影响行数范围、超时、审计和重放策略；默认禁止不确定结果后的自动重放。支持 `UPDATE`、`INSERT` 或 `DELETE` 不代表同时开放 DDL、多语句、存储过程或任意数据库脚本。

数据库能力按独立演进阶段交付：P0 完成只读查询和可扩展执行接口；后续 SQL 工具阶段先提供人工查询，再按权限与确认机制增加人工写入；再后续的流程写库阶段引入 `SqlContract` 和受控 `sql.execute`。DDL、存储过程、批处理和更多数据库 Adapter 继续按真实需求单独评估。

### 4.10 后续 SqlContract 的职责

`SqlContract` 不是接收任意 SQL 的通用执行器，而是一项具体、命名、版本化 SQL 操作的资产契约。通用 SQL 执行能力负责连接解析、参数绑定、数据库调用、事务、超时、类型归一和技术结果；`SqlContract` 在其上固定业务输入、静态 SQL、参数映射、结果约束、风险规则和对调用者公开的业务输出。

后续 `SqlContract` 至少必须声明稳定资产 ID、`query | execute` 操作类别、逻辑 `connectionRef`、类型化输入、单条静态语句、参数映射以及公开输出。查询契约还必须声明结果数量约束；写契约还必须声明允许的语句能力、事务策略、预期影响行数范围和重放策略。调用步骤只能传入契约声明的输入，不得覆盖 SQL、连接、操作类别、事务或风险限制。

SQL 运行结果分为两层：执行能力产生统一技术结果，查询至少为 `rows + meta`，写操作至少为 `affectedRows + meta`；`SqlContract` 再从技术结果中投影稳定的命名业务输出。后续步骤应优先依赖契约业务输出，而不是穿透依赖数据库表名、列名或驱动原始响应。

只读查询可以继续以内联 `sql.query` 或 Flow 交付；只有出现明确复用、集中治理或稳定业务输出需求时才需要查询型 `SqlContract`。自动化流程写操作则必须使用已发布写入型 `SqlContract`。两类 Contract 最终编译为相同的版本化 SQL 执行动作计划，数据库 Adapter 不应感知资产文件形态。

### 4.11 Flow 输入输出与共享类型系统

Flow、ApiContract、PageContract 的 `route` 以及未来 SqlContract 必须共享同一套版本化的受限结构化类型系统，使调用关系可以在发布时进行一致的输入输出兼容性检查。普通可序列化资产值的首期类型固定为 `string`、`integer`、`decimal`、`boolean`、`date`、`datetime`、`object`、`list` 和 `json`。

- `decimal` 用于金额和其他精确小数，不提供语义不稳定的二进制 `float` 类型。
- `date` 使用 `YYYY-MM-DD`；`datetime` 使用必须带时区的 RFC 3339 表示。
- `object` 必须声明已知字段并默认拒绝未声明字段；`list` 必须声明元素类型。
- `json` 表示任意 JSON 兼容值，是外部响应结构无法静态描述时的显式逃生口；使用它意味着放弃相应子树的字段级静态校验，不得把全部业务对象默认声明为 `json`。
- `null` 不作为独立类型。是否可以省略由 `required` 表达，是否可以显式传入空值由 `nullable` 表达；二者不得混为同一语义。

Browser 页面实例使用运行时专用不透明能力类型 `pageHandle`。它不属于上述九种普通资产值，也不等同于字符串：只能由 Browser 动作产生，只能在同一 Run、同一 BrowserContext 内通过 Step 或 Flow 的类型化输入输出传递。`pageHandle` 不得进入 DataSet、Scenario 外部输入、ApiContract/Page route 输入、`json`、模板或数据转换，也不得持久化后在恢复执行时重新使用；报告只保存不可复用的显示标识和页面元数据。跨 Run、跨 BrowserContext 或从普通字面量构造该类型必须拒绝。

每个 Flow 输入必须声明类型和 `required`，可选声明 `nullable` 与说明。首期 `required: false` 只表示调用时可以不传，不自动产生 `null` 或默认值；首期不支持输入默认值。调用者不得传入未声明输入，也不得依赖字符串、数字、布尔值、日期或对象之间的隐式转换。

Flow 输出必须同时声明类型和 `value`，其中 `value` 是普通字面量或合法值节点。Flow 成功结束前必须产生并按声明类型校验全部根级输出；输出缺失或类型不兼容以结构化 `data` 类失败结束。调用者只能读取 Flow 的公开输出，不得穿透访问其内部步骤、技术动作结果或局部变量。

当引用来源的类型可以静态确定时，编译器必须在发布前拒绝不兼容调用；当类型只能由外部响应或运行时数据决定时，Engine 必须在进入被调用资产前和输出公开前执行运行时校验。所有需要改变类型的操作必须使用明确的 `data.transform`，不得由调用、引用、模板或断言隐式完成。

首期不支持联合类型、递归类型、类型继承和用户自定义命名类型。后续需要复用复杂业务 Schema 时应基于真实资产评估命名类型或 Schema 资产，不能在 P0 直接开放完整 JSON Schema 语法。

## 5. 资产源、校验与发布

### 5.1 首期 Git 模式

- 一个测试项目绑定一个标准 Git URL、一个默认分支和一个资产根目录。
- 平台首期只读 Git，不写回、提交或创建 PR。
- P0 私有仓库认证支持 HTTPS Token/PAT 和 SSH Deploy Key。凭据由平台加密保存并使用独立版本引用；HTTPS 必须校验证书，SSH 必须校验并固定目标主机公钥，主机公钥变化时同步失败并等待管理员明确更新，不能自动接受。
- P0 不使用平台用户的个人 OAuth 授权、交互式 Git 登录、本机 Git Credential Helper 或用户 SSH Agent，也不支持把用户名密码、Token 或私钥写入 Git URL。
- 用户从 Web 手动触发同步；每次同步把默认分支当时解析出的 commit 固定为一个“已同步提交”，完整获取后校验资产根目录下的全部 YAML。同步过程中分支继续移动不得改变本次固定的 commit。
- 任一 YAML 资产结构、引用或策略校验失败时，整个资产根不得发布；未被当前 Scenario 引用的非法资产也不能被静默忽略。
- 有发布权限的用户只能从平台仍保存且已校验通过的“已同步提交”中显式选择并发布整个资产根的原子修订，包括选择较早的已同步版本；P0 不接受用户输入任意 SHA，也不发布平台从未完整获取和校验的提交，不发布单个资产或临时依赖闭包。
- 平台必须保存该修订的完整不可变内容、Git 提交标识、内容摘要和验证结果。发布后即使远程 Git 仓库不可用、分支移动或被删除，已发布修订仍可被验证和运行。
- 每个测试项目维护一个当前活动发布修订。发布新修订时原子切换活动引用，历史已发布修订保持不可变；获权用户可以重新激活平台仍完整保存且当前能力兼容的历史已发布修订，形成新的激活事件并审计，不修改旧内容、不写回 Git，也不要求重新输入 Git SHA。
- 已形成快照的 Run 继续使用原修订；切换或回退后创建的新手动 Run 与新定时触发使用新的活动修订。回退不自动重跑失败 Run、不恢复已拒绝 Run、不补跑历史定时触发。若历史修订需要当前平台不再支持的 DSL、操作符、Adapter 或 Worker 能力，必须在切换活动引用前拒绝并说明不兼容项。
- 私有仓库凭据只保存在平台连接配置中，不得进入 YAML、运行快照、日志、报告或制品。远端强推、提交删除或历史改写不得改变已发布修订。
- P0 不支持 Git submodule 或 LFS；资产根发现相应引用时必须拒绝发布，不能在 Worker 执行时临时拉取外部内容。
- 运行只能引用已发布修订及其不可变快照。
- 所有资产引用必须位于资产根目录内；禁止绝对路径、路径穿越、符号链接逃逸、根目录外文件和远程 URL 引用。

### 5.2 后续演进

- P1：Web 草稿编辑，并以 Git 提交或 PR 回写。
- P2：从接口文档或接口 `curl` 示例提取信息，由 Agent 生成 `ApiContract` 与 `ApiCheckSet` 候选 YAML 草稿；生成结果必须保留来源引用和不确定假设，并经过 Schema、引用、风险校验、人工审阅和显式发布后才可运行。输入中的 Token、Cookie、密码等真实凭据不得写入草稿，Agent 不得自动发布或绕过现有 Git、权限和审计边界。

## 6. 执行与认证

### 6.1 组合执行

- Scenario 必须支持 API、Browser 和 SQL 只读查询的顺序组合，以及显式步骤输出到后续步骤的业务数据传递。
- Flow 必须具备显式输入、显式输出和可静态校验的引用关系。
- 步骤输出保持不可变；需要拼接、计算、筛选、分组或重组时，必须产生新的转换步骤输出，不得原地修改来源步骤的结果。
- 动态数据加工使用受版本管理的通用转换操作符。操作符必须声明输入、输出和错误语义，并支持编译期校验；首期禁止在 YAML 中执行任意 Python、JavaScript、Shell 或其他脚本。
- 通用内核只提供跨项目成立的对象、字符串、金额、集合、值和日期操作；公司或项目专属计算必须由资产 Flow 或受控 Adapter 承担，不得成为内核操作符。
- 断言操作符采用简短且通行的英文名称，但不得以减少断言能力换取表面精简。比较类操作符首期命名为 `eq`、`ne`、`gt`、`gte`、`lt`、`lte`；语义类操作符使用清晰的完整单词，包括 `exists`、`notExists`、`contains`、`notContains` 和 `matches`。
- 断言操作符统一使用小驼峰命名，不使用 `==`、`>=` 等符号作为 YAML 操作符，也不使用 `compare + relation` 或通用 `negate` 组合隐藏实际断言语义。运行报告和结构化日志必须记录最终操作符、实际值类型、期望值及断言结果。
- 断言操作符必须通过版本化注册表扩展。编译器和 Worker 必须依据同一版本的名称、输入类型和语义进行校验；已发布修订必须固化其操作符版本，Worker 不支持时必须在执行前拒绝，而不是在运行中降级或猜测语义。

Step 首期统一采用“平铺公共外壳 + `action` 判别动作专属字段”的严格结构，不再在每种动作外额外包一层对象。下面示例同时展示 API 调用、显式执行身份、步骤断言和不可变输出：

```yaml
- id: createOrder
  name: 创建订单
  action: api.call
  contractRef: api.order.create

  auth:
    actorRef: buyer

  inputs:
    amount:
      $ref: inputs.amount

  timeoutMs: 30000

  assertions:
    - id: created_status
      actual:
        $ref: result.status
      op: eq
      expected: 200

  outputs:
    orderNo:
      type: string
      value:
        $ref: result.body.data.orderNo
```

Step 公共外壳只允许 `id`、`name`、`action`、`auth`、`timeoutMs`、`assertions`、`outputs`、`wait` 和 `replay`；其中字段是否必填及是否允许，由具体动作 Schema 约束。动作专属字段首期固定如下：

| `action` | 动作专属字段 |
| --- | --- |
| `api.call` | `contractRef`、`inputs` |
| `flow.call` | `flowRef`、`inputs` |
| `browser.open` | `pageRef`、`inputs` |
| `browser.click` | `pageRef`、`elementRef` |
| `browser.fill` | `pageRef`、`elementRef`、`value` |
| `browser.read` | `pageRef`、`elementRef` |
| `browser.screenshot` | `pageRef` |
| `sql.query` | `connectionRef`、`statement`、`params`、`maxRows` |
| `data.transform` | `operator`、`inputs` |
| `collection.map` | `source`、`flowRef`、`inputs` |

API 和 Browser Step 必须在自身步骤上显式声明执行身份，并且只能二选一：使用 `auth.actorRef` 引用被测系统身份，或者使用 `auth.mode: anonymous` 明确声明匿名访问。Flow 内每个 API/Browser Step 继续自行声明身份，不从 Scenario、Flow 或前一步继承默认账号。SQL、Flow 调用、数据转换和集合执行不得声明 `auth`；SQL 使用受控连接自身的凭据。

```yaml
auth:
  mode: anonymous
```

同一 Flow 或 Scenario 的 `steps + cleanup` 范围内，Step `id` 必须唯一。后续步骤只能通过 `steps.<stepId>.outputs.<name>` 读取已经公开的不可变输出；当前动作的 `result` 只在本 Step 的 `wait`、`assertions` 和 `outputs` 中可见。Step 输出必须声明 `type + value`，普通值按共享结构化类型系统校验，运行时能力值按其来源和作用域规则校验。所有未知公共字段、未知动作专属字段、字段与 `action` 不匹配以及首期不支持的 `when`、`retry` 字段都必须在发布前拒绝。

等待轮询是 Step 公共能力，但只有同时提供 `wait` 与显式重放授权时才允许再次执行动作。`wait.intervalMs` 和 `wait.maxAttempts` 定义有界尝试，`wait.until.assertions` 针对当次动作的 `result` 判断是否结束；`replay.allowedFor` 必须包含 `wait`，并通过 `reason` 说明为何本动作可安全用于等待。

```yaml
wait:
  intervalMs: 2000
  maxAttempts: 15
  until:
    assertions:
      - id: order_paid
        actual:
          $ref: result.body.data.status
        op: eq
        expected: PAID

replay:
  allowedFor:
    - wait
  reason: 订单详情查询可安全重复执行
```

每个 Step 的执行语义固定为：解析并校验输入，执行动作，执行该动作或 Contract 的成功语义，按 `wait` 进行有界重复并记录每次尝试，执行 Step `assertions`，计算并校验 `outputs`，最后一次性发布不可变输出。任何阶段失败都不得发布部分输出；动作重放继续遵守第 6.2 节的资格与冻结规则。

- Scenario 首期采用 `steps + cleanup` 两阶段模型，不另设隐式 setup 阶段；造数和业务前置步骤按真实顺序写入 `steps`。
- `steps` 结束或失败后，Engine 仍应按声明顺序尝试执行 `cleanup`。`cleanup` 可以引用此前成功产生的步骤输出；依赖输出不存在时必须明确记录跳过原因，不得使用空值继续执行。
- 主步骤结果与清理结果必须分别记录。清理成功不得覆盖主步骤失败；主步骤成功但任一 cleanup 失败时，Scenario 最终状态固定为 `failed`，同时保留主步骤成功事实和清理失败证据。
- `cleanup` 不是事务回滚机制。支付、退款、结算等不可逆操作不得作为可自动重试的通用清理动作；所有清理步骤继续受操作风险和重试资格约束。
- 首期不支持步骤级条件执行，DSL 校验器必须拒绝未支持的 `when` 字段。首期执行计划保持确定的顺序结构，同时结果模型预留 `skipped` 状态。
- 首期支持受限的有限集合执行：从 DataSet、Scenario 局部变量或先前步骤输出取得一个已存在的有限列表，严格按原顺序逐项调用一个已发布 Flow，并按原顺序聚合每次调用的显式输出。
- 集合执行为每次调用显式提供当前 `item`、从零开始的 `index` 和调用方声明的公共输入。被调用 Flow 的输入必须完整匹配，不能隐式读取集合步骤或 Scenario 的其他上下文。
- 首期集合执行不支持并发、嵌套循环、动态步骤体、`break`、`continue` 或无限循环；任一项失败时立即停止，并记录失败索引、输入摘要和已完成项结果。
- 集合执行的整体重放资格由被调用 Flow 的内部动作汇总，不能借由集合包装绕过步骤的重放限制。
- SQL 数据库必须由平台作为受控连接配置；YAML 仅可引用逻辑连接名，不得包含连接地址或凭据。
- 首期 SQL 能力仅允许参数化只读查询、结果投影和断言；写入和删除等操作不属于首期 Scenario 能力。
- API 和 Browser 认证必须按通道隔离；API 请求头或 Token 不能被当作浏览器登录态。
- BrowserContext 按 `(runId, environment, targetRef, actorRef)` 隔离。同一 Run 中相同组合的步骤和被调用 Flow 可以复用该 Context；任一维度不同都必须创建独立 Context，不能跨 Run 复用实例。
- Browser Cookie/Storage State 缓存只能作为新 Context 的初始化材料，不能把已有页面或 Context 本身交给新 Run。Run 结束后，无论成功、失败或平台中断，Worker 都必须尽力关闭全部页面并销毁 Context，销毁失败作为平台清理事件记录。
- 认证模型必须分离被测系统身份、逻辑目标系统、通道、认证 Profile 和凭据引用。`auth.actorRef` 引用项目内稳定的逻辑执行身份槽位，不表示平台角色、真实用户名或动态账号选择条件。
- 同一个 `actorRef` 可以按环境、目标系统和 API/Browser 通道绑定不同认证 Profile；解析结果必须唯一确定。零匹配或多匹配必须在执行前以 `rejected + configuration` 拒绝。
- P0 对 `(environment, targetRef, actorRef)` 使用排他身份租约，不按 API/Browser 通道拆分：同一组合同时只允许一个 Run 持有，其他 Run 排队等待。同一 Run 内的 API 与 Browser 步骤共享这一个租约；需要并行时必须配置不同的确定性身份槽位，例如 `buyer.primary` 与 `buyer.secondary`，不能提高同一账号的并发上限。
- Compiler 必须从完整确定性计划中列出本 Run 所需的全部身份租约，包括展开后的 Flow 和 Suite 成员。控制面按规范顺序一次性原子获取全部租约：任一租约不可用时 Run 保持 `queued` 且不得占有其他部分租约，全部获取成功后才能进入 `running`；执行中禁止按步骤追加租约。该规则避免多身份 Scenario 因部分占有、相互等待而死锁。
- 每个身份租约键独立按 Run 的 `queuedAt` FIFO 排队。一个 Run 只有在其所需每个键上都是最早等待者时，才有资格原子获取完整集合；在任一共享键上排在它之后的 Run 不得插队，但与这些键完全无关的 Run 可以继续运行。P0 不提供优先级或人工插队，Web 必须展示造成等待的身份键和占用/在先 Run。
- 身份租约在 Run 进入终态后释放。Worker 失联时由控制面按租约超时回收，但回收不得触发原 Run 重放。身份串行不替代业务数据隔离，资产仍必须使用本次 Run 产生的 `orderNo`、`orderItemId` 等稳定标识，不能查询该账号的“最新一条”记录。
- 运行快照必须记录 `actorRef`、最终解析的被测系统身份、认证 Profile 和凭据版本引用，但不得保存凭据明文。密码或 Token 轮换不得要求修改 YAML 中的 `actorRef`。
- 登录成功必须支持有效性校验，不能只依据 HTTP 200、Cookie 存在或页面跳转判断。
- 同一身份可在多个目标系统使用不同认证方式；平台必须支持多账号并存、显式切换和登录失效处理。
- API 可持久化会话缓存与 Browser 运行期会话必须分别定义隔离、有效期、失效、审计和销毁策略。
- P0 支持显式匿名、API 表单登录后提取 Token、API 表单或多步骤登录形成 Cookie Session、Browser 登录形成隔离 Cookie/Storage State，以及受控验证码认证 Adapter。每种 Profile 必须声明成功校验、有效期、失效条件和销毁方式。
- 受控验证码认证 Adapter 可以使用认证专用的 Redis 受控连接读取一次性验证码；Redis 地址、凭据和 Key 规则属于 Profile/Adapter 与平台连接配置，普通 Scenario 不得直接读取认证验证码或取得该连接凭据。
- API 认证 Profile 在发送业务请求前必须校验缓存 Token/Session。能够由有效期、有效性探针或明确失效标记在发送前判定无效时，平台自动执行登录，原子更新当前身份会话，并使用新鉴权发送尚未执行的业务请求；这属于认证建立，不计为业务动作重放。
- 如果业务请求已经发送后才通过 HTTP 401/403 或 Profile 声明的稳定业务错误判定会话失效，平台自动登录并更新后续步骤使用的鉴权，但当前请求默认不重发并以 `failed + auth / SESSION_INVALIDATED_AFTER_REQUEST` 结束。只有无业务副作用的只读 ApiContract 把 `authRefresh` 声明为契约上限，且当前 Step 的 `replay.allowedFor` 也申请 `authRefresh` 并填写理由时，才允许使用完全相同的冻结输入重试一次；最终资格取两者交集。
- 重新登录、会话版本变化和任何认证刷新重试都必须进入结构化时间线。登录失败时当前 Step 以 `failed + auth` 结束，不能回退使用旧 Token/Session。
- Browser 创建新页面前发现 Cookie/Storage State 无效时，可以重新认证并创建新 Context/页面；已有 `pageHandleRef` 的 Browser 动作发现会话失效时不得自动重建页面、导航或重放点击/填写，当前 Step 以 `failed + auth / SESSION_INVALIDATED` 结束。
- 静态 API Key、OAuth、短信人工输入及其他未被黄金流程证明必要的认证方式不属于 P0，后续按版本化 Profile 能力扩展。

### 6.2 重试与风险

- 首期不提供用户配置重试。
- 等待轮询、故障重试、主动重复和整段重跑都会再次执行动作，必须共用同一套重放资格模型；不得依据 GET、POST、Browser 动作名称或其他动作类型硬编码安全性。
- 首期采用步骤级人工重放声明。步骤配置等待轮询时，必须显式声明 `replay.allowedFor` 包含 `wait` 并填写可审阅的理由；未声明时默认禁止再次执行。
- `replay.allowedFor` 在 P0 只允许 `wait` 和 `authRefresh`，不因此开放网络故障重试、用户配置重试、主动重复或整段自动重跑。
- `authRefresh` 采用 Contract 上限与 Step 申请双重授权：ApiContract 的 `spec.replay.allowedFor` 和 Step 的 `replay.allowedFor` 必须同时包含 `authRefresh`，最终资格取两者交集。该用途只允许无业务副作用的只读 API 动作以冻结输入重试一次；创建、修改、支付、结算、退款、Browser 动作和其他不可逆动作声明时必须在发布前拒绝。
- 轮询开始前必须冻结动作的目标系统、执行身份和全部解析后输入；每次尝试复用完全相同的请求参数及幂等键，时间、随机数、UUID 等动态值不得在每次尝试时重新生成。
- 每次尝试都必须写入结构化时间线；超时后保存最后一次结果、尝试次数和明确失败原因。步骤的重放声明必须进入发布修订和运行快照。
- 其他重放用途后续同样采用能力契约声明最大范围、步骤只申请本次用途的模型；步骤可以收紧但不能放宽契约。
- 内核必须为未来重试保留操作风险、幂等保证、错误匹配和可重试资格模型；不可逆动作在没有明确契约授权时默认禁止自动重放。

### 6.3 首期运行入口

- 所有运行入口统一形成 `ExecutableInvocation`，再经过输入绑定形成运行快照。控制面、定时任务、后续平台 API 和 MCP 不得各自定义一套直接传给 Worker 的参数格式。
- 每个手动运行调用必须携带由客户端生成的稳定 `invocationId`，服务端以 `userId + invocationId` 作为 24 小时幂等键。窗口内相同 ID 与相同规范化调用内容返回原 Run，不创建新快照或新队列项；相同 ID 对应不同资产、环境、策略或其他调用内容时以结构化幂等冲突拒绝。用户显式再次运行必须生成新的 `invocationId`。按钮防双击只能作为交互优化，不能替代服务端幂等；后续平台 API 与 MCP 复用同一调用幂等协议。
- P0 的 Scenario 不声明外部输入，`inputs` 根不对 Scenario 开放；业务数据只能来自已绑定 DataSet、Scenario 局部变量、Step 内联值和先前步骤显式输出。
- P0 的 `InvocationInputBinding` 必须为空，任何非空 Scenario 输入绑定都必须在快照形成前拒绝。平台仍应让 InputBinder 参与统一调用链，并在运行快照中固化空的 `ResolvedScenarioInputs`，避免 Worker 或 Compiler 直接读取 Web 表单、定时任务或外部入口的原始参数。
- 后续版本可以增加类型化 `ScenarioInputDefinition`，并由手动任务、定时任务、Suite、平台 API 或 MCP 提供 `InvocationInputBinding`。输入必须在运行快照形成前完成必填性、类型、可空性、未知字段、来源和访问级别校验；Worker 始终只消费已解析的不可变值。
- Suite 在 P0 只有确定的 `scenarioRef`；后续成员级输入映射必须复用同一输入绑定协议。日志、报告和审计模型应为输入来源、脱敏和访问事件预留兼容扩展位置，但 P0 不展示不存在的 Scenario 输入功能。
- Web 支持运行已发布的 Scenario、Suite 和 `ApiCheckSet`。
- Web 首期只运行 YAML 已固定的数据，不支持临时表单参数、自由请求调试台或运行时修改 YAML。
- 支持手动运行与定时运行。
- 同一定时任务采用 FIFO 串行队列；上一实例未结束时，下一实例排队等待。
- 平台默认展示时区和新建定时任务的默认时区为中国时区 `Asia/Shanghai`（UTC+8），但每个定时任务仍必须显式保存 IANA 时区；所有持久化时间点同时使用 UTC，界面按任务时区或平台默认时区展示，不能依赖服务器本地时区。平台恢复后默认跳过停机期间错过的触发，不补跑历史触发；同一任务最多保留一个待执行实例，更多触发记录为已跳过。
- IANA 时区发生夏令时变化时，本地计划时间不存在则记录一次 `skipped` 且不补跑；同一本地时间出现两次时只触发一次，选择较早的 UTC 时刻。每次触发保存本地计划时间、IANA 时区、UTC `scheduledFireTime` 和采用的时区规则版本。`Asia/Shanghai` 当前没有夏令时，这些规则用于保证协议完整和未来部署兼容。
- 定时触发以 `scheduleRef + scheduledFireTime` 作为幂等键；同一计划时间只能形成一个运行请求，重复投递不得创建重复 Run。
- 在控制面健康、系统时间已同步且不存在停机跳过条件时，Run 不得早于 `scheduledFireTime` 创建，且 99% 的定时触发必须在计划时间后 60 秒内完成 Run 创建与快照冻结。该指标只衡量创建并入队，不要求 Run 在 60 秒内取得身份租约或 Worker 槽位。
- 定时任务和排队实例在触发时冻结运行快照，而不是在实际开始执行时读取最新状态。
- 定时任务属于测试项目，不依附创建者的登录会话。创建、修改和启用任务时必须按操作者当前权限校验并审计；任务保存 `createdBy`、`lastModifiedBy` 和不可变配置版本。创建者之后被禁用或撤权时，已经启用的任务继续由平台调度器按已保存版本触发，触发事件记录调度器身份和任务版本，不伪装成创建者在线操作。管理员必须能按创建者查询并批量停用其历史任务。
- 被禁用用户不再接收站内通知；定时任务选择的项目钉钉渠道不因创建者状态变化而停用。任务后续修改或重新启用仍要求当前操作者具备相应权限。
- 运行快照至少冻结发布修订与内容摘要、DSL/操作符版本、目标系统和受控连接绑定版本、Adapter/Worker 能力版本、`actorRef` 解析结果、认证 Profile 版本、凭据版本引用、`ResolvedScenarioInputs`、任务策略、报告访问模式和通知配置，但绝不保存凭据明文。
- 运行快照和确定性计划形成后，Compiler 必须枚举全部身份租约键；控制面只有原子获取完整租约集合后才能把 Run 从 `queued` 转为 `running`。租约不足时不得部分占有，也不得让 Worker 执行到相关步骤时再申请。
- Run 进入 `queued` 后的默认最长等待时间为 24 小时，平台允许全局配置 1 至 72 小时，并将实际值写入运行快照。超过期限时 Run 以 `failed + timeout / QUEUE_WAIT_EXCEEDED` 结束，不获取身份租约、不执行任何业务动作，也不自动创建替代 Run；P0 不新增 `expired` 状态。
- 普通凭据轮换产生新版本；已经形成快照的 Run 继续引用原版本。紧急撤销优先于可重复执行：尚未使用被撤销凭据的排队 Run 必须在执行前以 `rejected + policy` 结束，不得自动切换到新凭据；运行中的 Run 在下一次取得或刷新该凭据时失败并记录撤销事实。
- 首期结果模型保留 `cancelled` 状态；手动取消属于可选 P1 能力。人工等待及其 `waiting_input` 状态后续通过版本化状态模型扩展，不进入 P0。
- 手动运行以及定时任务的创建或修改统一展示资产、修订、环境和执行身份摘要，并审计操作者与实际快照。P0 不区分特殊高风险 Scenario，不增加风险等级、专用运行权限、二次确认或预授权模型。
- 每次外部动作尝试必须先生成稳定 `attemptId`，并在发送请求、执行 SQL 或操作浏览器前持久化动作、目标、冻结输入摘要和 `started` 事件。无法持久化该事实时，Worker 不得发起外部动作。
- 动作完成后必须持久化成功、明确失败或结果不确定事实；结果事实未成功持久化前不得进入下一 Step。若外部动作可能已发生但结果无法确认，Run 以 `failed + platform / ACTION_OUTCOME_UNKNOWN` 结束，不自动重放该动作或整个 Run。
- 出现 `ACTION_OUTCOME_UNKNOWN` 后，Engine 必须跳过全部资产声明的 cleanup，并为每个未执行清理步骤记录 `OUTCOME_UNKNOWN` 跳过原因；不得自动查询、取消、退款、补偿或回滚业务状态。Engine 仍须关闭 BrowserContext、释放身份租约和执行其他平台资源清理。用户只能依据已保存的 `attemptId`、冻结输入摘要和外部只读证据人工判断，再显式创建新 Run。
- Worker 到控制面的结构化事件允许至少一次投递，但每个事件必须具有稳定 `eventId` 并幂等去重。已确认持久化的动作与状态事件不得因 Worker 重启、重复投递或报告重建而丢失或重复计数。

### 6.4 状态与失败模型

- 生命周期状态与失败原因必须分离。状态只描述是否排队、执行及其最终结果；失败类别和错误码描述失败原因，不得为每一种错误不断增加专用状态。
- Run 首期状态固定为 `queued`、`running`、`passed`、`failed`、`cancelled`、`rejected`。`rejected` 表示 Run 尚未进入 `running`、未执行任何业务动作时，因资产、配置、策略或平台受理问题而终止；它可以发生在入队前，也可以发生在排队期间，并且必须保留拒绝记录和结构化原因。
- Step 首期状态固定为 `pending`、`running`、`passed`、`failed`、`skipped`、`cancelled`。`skipped` 必须记录明确原因；不得仅以空输出或缺少时间线推断步骤被跳过。
- `timeout`、`auth`、`assertion` 等属于失败类别，不属于生命周期状态。失败记录至少包含稳定的 `category`、稳定的 `code`、可读的 `message`、发生阶段及关联步骤。
- 首期失败类别固定为：`asset`（资产结构、引用或能力声明）、`configuration`（环境、目标、凭据或连接绑定）、`policy`（安全或执行策略）、`data`（引用、类型、模板、选择或转换）、`auth`（登录、会话和有效性校验）、`transport`（DNS、连接、TLS 和网络协议）、`timeout`（动作、等待或运行超时）、`action`（执行器无法完成动作）、`assertion`（结果不满足断言）和 `platform`（Worker、队列、存储或内核异常）。
- 失败类别用于统一筛选、趋势和责任定位，具体原因由类别下可扩展的稳定错误码表达。API、Browser、SQL、ES 等动作类型不得成为失败类别；它们由步骤动作元数据区分。
- HTTP 4xx/5xx 表示已经获得协议响应，不得归类为 `transport`。该响应是否使步骤失败，由 ApiContract 的成功语义和显式断言共同决定。
- `skipped` 和 `cancelled` 不属于失败，必须分别记录结构化 `skipReason` 和 `cancelReason`。`cleanup` 也不属于失败类别，继续通过 `phase: cleanup` 表达。
- 同一失败类别可以出现在执行前拒绝或执行中失败。例如队列前缺少目标绑定记录为 `rejected + configuration`，运行中的登录失败记录为 `failed + auth`。
- 主步骤与清理步骤共用同一套 Step 状态和失败结构，并通过 `phase: main | cleanup` 区分。清理阶段不得另建一套不兼容的状态或错误模型。
- 主步骤全部通过但任一 cleanup 步骤失败时，Scenario 最终状态为 `failed`，同时保留主步骤成功事实和 `phase: cleanup` 的失败记录。
- 主步骤失败时，Scenario 最终状态始终为 `failed`；原始主步骤失败是主要原因，cleanup 的通过、失败或跳过结果独立保存，不得覆盖主要原因。
- Suite 采用继续执行策略时，成员失败不阻止后续成员，但任一成员失败都会使最终 Suite Run 为 `failed`。ApiCheckSet 默认执行全部变体，任一变体失败都会使整体 Run 为 `failed`，每个变体仍保留独立结果。
- Scenario 趋势只有主步骤和 cleanup 全部通过时才计为通过；Suite 和 ApiCheckSet 的聚合结果不得覆盖成员级事实。
- 状态值首期保持封闭并由协议版本约束；失败类别和错误码允许按兼容规则扩展。控制面遇到未知失败码时仍应按其类别和通用字段展示，不能丢弃原始错误信息。
- 请求在进入队列前因平台不可用而不能受理时，保存为 `rejected + platform`；已经进入运行态后 Worker 租约丢失或执行面不可恢复中断时，保存为 `failed + platform`。平台恢复后不得自动重放原 Scenario，用户需要显式创建新的 Run。
- P0 不提供手动取消入口，但保留 `cancelled` 协议状态供后续版本使用；平台停机、Worker 失联、超时和策略拒绝均不得伪装成 `cancelled`。

### 6.5 P0 时间与资源上限

- `api.call` 和 `sql.query` 的默认单次动作超时为 30 秒，Browser 动作默认超时为 60 秒。Step 可以通过 `timeoutMs` 在平台允许范围内收紧或放宽，但不能超过整个 Run 的剩余时间预算；实际默认值、上限和 Step 覆盖值必须进入运行快照和时间线。
- 一个 Step 的完整 `wait` 过程最多持续 10 分钟，包括首次执行、间隔和全部后续尝试；`intervalMs + maxAttempts` 推导出的最坏时长超过上限时必须在发布或编译时拒绝。
- Run 从 `running` 开始计算的主执行时间最多 2 小时。主流程达到上限后停止启动新的主步骤，以 `failed + timeout / RUN_TIMEOUT` 记录主结果；已经发出的外部请求不得被假定为未执行，也不得自动重放。
- 主流程因成功、失败或超时结束后，为能够安全执行且依赖已满足的 cleanup 额外保留最多 10 分钟。cleanup 超过该预算时停止启动后续清理步骤并记录 `timeout / CLEANUP_TIMEOUT`；额外预算不改变主流程超时事实，也不能用来继续普通业务步骤。
- Suite 最多包含 100 个 Scenario，ApiCheckSet 最多包含 100 个变体，单次 `collection.map` 最多处理 100 项。静态可知的超限必须在发布前拒绝，运行时集合超过上限时以 `failed + policy / COLLECTION_ITEM_LIMIT_EXCEEDED` 结束，不能只执行前 100 项。
- 单个 Run 最多执行 1000 个动作实例，计数包括展开后的 Flow、Suite 成员、ApiCheckSet 变体、collection 项、cleanup 和 wait/authRefresh 产生的每次动作尝试。编译期可以证明超限时在进入 `running` 前拒绝；只能运行时确定时，以 `failed + policy / RUN_ACTION_LIMIT_EXCEEDED` 结束。
- `sql.query.maxRows` 的 P0 平台上限为 1000。超过上限的资产在发布前拒绝；查询达到声明的合法 `maxRows` 时继续按 `truncated: true` 表达，不把截断伪装成完整结果。
- 单个 HTTP 响应体或单个制品最多 50 MiB，单个 Run 的制品累计最多 500 MiB。超过单体上限的响应或制品以 `failed + action / PAYLOAD_SIZE_LIMIT_EXCEEDED` 结束；超过 Run 累计额度时以 `failed + policy / RUN_ARTIFACT_QUOTA_EXCEEDED` 结束。不得静默丢弃响应、截图或制品后将 Step 判为通过。
- 上述数值是 P0 产品硬上限。平台可以在其范围内提供更严格的全局部署配置，但 P0 不开放项目、YAML 或单次运行自行提高上限；运行快照必须记录实际生效策略。

## 7. 凭据、数据安全与保留

- 被测系统凭据由平台 Web 管理、加密存储，并以别名被资产引用；Worker 仅在必要时读取。
- 凭据、Git Token/Deploy Key、受控连接密码、通知渠道密钥和 raw 证据使用信封加密：每份敏感数据使用随机数据密钥加密，数据密钥再由版本化平台主密钥保护。主密钥由部署系统通过独立 Secret 或只读挂载提供，不进入数据库、Git、普通配置、日志或制品；P0 不强制依赖云 KMS，但必须保留可替换的主密钥提供接口。
- 主密钥轮换后，新写入数据使用新版本；旧版本主密钥保留到相关密文全部重新加密或按保留策略过期。数据库/制品备份与主密钥恢复副本必须分开保管和授权。启动时缺少所需主密钥版本或无法解密关键配置，平台必须失败关闭，不能静默生成新密钥、清空密文或降级为明文。备份恢复演练必须同时证明主密钥可恢复及历史密文可解密。
- 获权管理员可临时查看或复制明文凭据；查看、复制、修改和使用必须审计。
- 平台用户密码与被测系统凭据必须分别管理。
- 报告访问模式支持 `masked`、`revealable`、`raw`。角色到查看、揭示和 raw 访问能力的映射在角色权限功能中配置，平台代码不得按角色名称写死结果访问级别；每次查看和揭示都按当前授权校验并记录审计。
- `masked` 按配置隐藏业务字段和认证值；`revealable` 允许获权用户逐项查看真实值；`raw` 展示平台实际捕获的完整业务请求响应，包括请求头、认证头、Token、Cookie、查询参数、请求体，以及请求中实际发送的被测系统登录密码、支付密码和验证码。原始证据必须加密保存，不能写入普通 Worker 控制台日志。
- 脱敏配置保持两级：测试项目提供默认规则，目标系统可以覆盖该默认；目标系统规则优先。P0 不增加步骤级、单次运行级或任意表达式规则，YAML 不能修改平台脱敏策略。运行快照记录当次策略版本，查看历史证据时同时记录实际使用的查看模式和当前权限。
- P0 不对截图执行文字、区域、像素或 OCR 脱敏，也不设置截图专属权限或使截图参与 `masked`、`revealable`、`raw` 分级。任何已经拥有该 Run 查看权限的用户都可以在 Web 中查看平台保存的原始截图；截图可能包含真实业务数据，平台必须在项目配置和报告界面明确提示这一事实。后续如有需求，再增加版本化图片处理规则和独立访问能力。
- 浏览器下载文件和其他非截图制品继续按所属项目、目标系统及报告访问策略处理。平台自身账号密码、Git 凭据和受控连接凭据不属于业务请求证据，任何报告模式都不得将它们混入运行数据。
- P0 只提供 raw 在线查看，不提供 raw 报告、原始请求响应或原始制品的下载与导出，也不定义 `export_raw_run_data` 权限。后续开放导出时必须增加独立能力、审计和项目级授权扩展，不能静默扩大 `view_raw_run_data`。
- P0 产品界面不提供截图下载或导出；这属于交付范围限制，而不是截图专属权限模型。
- 运行数据默认保留 30 天，平台允许配置的最大保留期为 180 天。到期后的主存储删除 SLA 为 24 小时，备份和异地副本最迟在 7 天内删除；删除覆盖运行、报告、日志、制品和趋势样本，只保留不含业务数据的清理审计事件。
- P0 不提供手工删除单个 Run、报告、日志、请求响应、截图或其他制品的 Web 操作或 API，超管也不能绕过保留策略直接删除。项目归档不触发这些数据的提前删除；确需提前清理时，只能由具备 `manage_retention_policy` 的用户缩短保留期，并遵守影响预览、二次确认、删除 SLA 和清理审计。
- `manage_retention_policy` 允许调整未来及尚未到期数据的策略，但不能恢复已删除数据，也不能突破 180 天上限。
- 缩短保留期前必须展示将受影响的数据范围并二次确认；确认后，已超过新期限的数据进入同一删除 SLA。延长保留期只影响尚未删除的数据，不能恢复已经删除的记录或制品。
- 资产发布，目标系统、受控连接、身份、凭据、角色、权限和策略的变更，项目归档与恢复，raw/revealable 查看，凭据揭示，密码管理，以及到期删除等关键操作必须写入审计事件。事件至少包含稳定审计 ID、操作者、动作、对象类型与引用、UTC 发生时间、结果、非敏感变更摘要、策略版本和可用的请求追踪标识。
- 审计记录必须只追加，平台 Web 不允许修改或手工删除单条审计事件。P0 通过数据库约束、权限隔离和备份保护审计数据，不实现 WORM 存储、密码学签名或外部合规归档。
- 具备 `view_audit` 能力的用户可以在 Web 中按操作者、动作、对象、结果和时间范围查询审计事件。P0 只提供在线查询，不提供审计导出、外部 SIEM 接入或专用合规报告。
- 审计事件默认保留 365 天，平台策略只允许配置为 90 至 730 天；P0 不支持永久保留。缩短审计保留期前必须展示影响范围并二次确认，审计删除作业本身继续产生审计事件。审计事件不得保存业务请求响应、Token、Cookie、密码、验证码、Git 凭据或受控连接凭据明文；对象引用和非敏感变更摘要必须足以追溯操作，不得以“防止泄露”为由只记录模糊文本。
- 必须审计的操作采用失败关闭：raw/revealable 查看或凭据揭示必须先持久化访问事件，失败时不得返回真实值；权限、平台配置、项目归档恢复等持久化变更与审计事件在同一数据库事务提交；Worker 获取或使用凭据执行外部动作前必须先保存关联 `runId`、`attemptId` 和凭据版本引用的使用事件，失败时不得发起外部动作。审计查询失败只影响审计页面，不中断已经运行的无关 Run。

## 8. 用户、角色与授权

平台使用本地账号密码。用户可以自行注册，注册成功后立即激活并自动获得普通用户角色，可以运行已发布资产并查看自己的 `masked` 结果；管理员后续负责升权、换角色或禁用账号。公共注册不能直接获得管理员或超管能力。密码重置由管理员或超管发起，首期不做邮件找回。

- 自助注册只要求登录名、显示名称和密码，并拒绝平台维护的常见弱密码。同一 IP 在任意连续 10 分钟内最多提交 10 次注册请求，同一规范化登录名在任意连续 10 分钟内最多尝试 5 次；任一维度超限都返回统一限流提示，不暴露登录名是否已经存在，窗口结束后自动恢复。上述阈值是 P0 固定默认值，后续如有实际需求再开放部署级配置。注册成功后必须写入账号创建、默认角色分配和登录事件，限流命中记录不含密码的安全事件。

- 新部署通过一次性 CLI 或一次性 Bootstrap Token 创建首个超管。首次成功后引导能力立即失效，公共注册入口永远不能创建管理员或超管；之后只能由已有授权账号管理用户和角色。备份恢复沿用已恢复的授权关系，不重新开放 Bootstrap。
- 每个平台用户具有不可变内部 `userId`，审计、任务、运行和其他历史事实始终通过该 ID 关联。登录名创建后不可修改、不可重复使用；显示名称可以修改，审计事件同时保存 `userId` 与操作发生时的显示名称快照。账号状态固定为 `pending`、`active`、`disabled`：P0 公共注册直接创建 `active` 用户，`pending` 仅为后续受邀或管理员预创建账号保留；P0 只允许禁用，不提供永久删除或登录名回收复用。后续如需清除员工个人信息，应设计不破坏审计主体的匿名化能力。
- 密码至少 6 个字符，不强制大小写、数字或特殊字符组合，但必须拒绝平台维护的常见弱密码。密码只以 Argon2id 或等价强度的单向密码哈希保存，禁止明文或可逆加密保存平台账号密码。
- 同一账号连续登录失败 10 次后锁定 15 分钟。登录响应不得暴露账号是否存在；失败计数、锁定、解锁和管理员重置必须审计。
- Web 登录使用服务端保存的高熵随机不透明会话标识，浏览器只通过 `HttpOnly` Cookie 持有标识，不使用存放在浏览器中的 JWT 作为 Web 会话。登录成功、重新认证和权限提升后必须轮换会话标识，旧标识立即失效。
- 登录会话空闲 8 小时失效，绝对有效期最长 24 小时。密码重置、账号禁用以及管理员或用户执行“退出全部会话”后，已有服务端会话必须立即失效；角色或能力撤销继续按当前授权即时生效。
- 所有改变服务端状态的 Web 请求必须同时通过 CSRF Token 与受信任 `Origin`/同源校验；仅 `SameSite` Cookie 不能替代 CSRF 防护。CORS 默认只允许平台配置的自身来源，不允许通配来源携带凭据。登录、登出、密码与权限管理、运行触发、raw/revealable 查看和凭据揭示均必须遵守相应来源与会话校验。
- 后续平台 API 或 MCP 使用独立的机器调用凭据与权限边界，不复用浏览器 Cookie、CSRF Token 或 Web 会话。
- 揭示或复制被测系统凭据、修改角色/能力授权、重置他人平台密码和创建 Worker 一次性注册 Token，要求当前用户在最近 15 分钟内完成过平台密码重新认证。超过窗口时只要求重新输入当前用户密码，不强制退出或丢失正在编辑的非敏感表单；成功后轮换会话标识并记录审计。查看 raw/revealable 运行数据、管理普通项目名称、通知接收人、定时任务或查询审计不要求重复认证，继续依赖当前权限和审计。后续 SSO/MFA 可以替换认证方式，但不得改变这些操作要求近期认证的能力边界。
- MFA、邮件找回和第三方 SSO 不属于 P0，后续作为独立认证能力扩展。

首期提供超管、管理员、测试人员、普通用户、只读人员五类全局角色，不增加“测试开发”角色，也不按测试项目划分授权。角色名称和初始权限模板是产品预置项，但角色到功能模块、操作能力和结果访问能力的映射必须能在角色权限功能或平台整体配置区域调整，不能写死在控制面、Engine 或 Worker 中。测试开发由测试人员角色叠加发布能力表达。

- 超管：管理管理员、角色、全局策略、审计和全部平台配置。
- 管理员：管理用户角色与账号状态、重置平台密码，管理项目、环境、目标系统、受控连接、被测系统身份、认证 Profile、凭据和定时任务。
- 测试人员初始模板：同步并校验资产，发起手动或定时运行，查看全局 `masked` / `revealable` 结果。
- 普通用户初始模板：可以浏览并手动运行平台内所有测试项目的已发布资产，只查看自己的 `masked` 结果；P0 没有按项目隐藏资产或限制运行的授权规则。
- 只读人员初始模板：查看允许访问的 `masked` 结果和趋势，不能触发运行。
- 测试人员、普通用户和只读人员的上述描述是初始权限模板；部署管理员可以在受审计的权限配置中调整功能模块和数据访问能力。修改权限不改变已经形成的运行事实，但会立即影响后续查看、揭示和新建任务授权。

权限目录至少包含以下稳定能力标识，并允许通过权限配置授予角色：`publish_asset`、`reveal_credential`、`view_revealable_run_data`、`view_raw_run_data`、`view_audit`、`manage_notification_channel`、`manage_redaction_policy`、`manage_retention_policy`、`manage_authorization`。能力的授予、使用、变更和撤销必须全量审计。拥有 `publish_asset` 的用户可以直接发布已验证修订，不增加额外审批流；用户只有在权限配置允许时才能揭示、查看 raw 数据或查询审计，不能通过运行表单自行提升权限。`view_audit` 与 `manage_notification_channel` 的初始模板只授予超管，但后续仍由全局角色权限配置调整，不在代码中按角色名称写死。
- `manage_authorization` 的初始模板只授予超管，后续是否授予其他角色仍由权限配置决定。平台必须阻止删除、禁用或撤权后导致系统中不存在任何可管理授权账号的操作；权限撤销对后续查看、揭示和新建任务立即生效。
- P0 的角色与能力授权范围是整个平台，不按测试项目分配。具备运行能力的用户默认可以浏览并运行所有测试项目的已发布资产；这不扩大其结果访问范围，普通用户仍只能查看自己的 `masked` 结果。权限判定协议应保留可选资源作用域扩展位置，但 P0 不展示或接受项目级授权配置；后续增加项目级授权时不得改变现有能力标识的含义。

## 9. 结果、日志、报告与趋势

每次运行必须保存并可查询：总体结果、结构化失败原因、按顺序的步骤时间线、接口请求响应、UI 截图、断言结果、失败原因及其他制品。

运行日志必须是结构化事件，而不是解析控制台文本；它必须足以还原整体运行顺序、步骤、输入、已解析变量、输出、请求响应、认证状态变化、重试和错误。日志与报告必须遵守第 7 节的脱敏和访问规则。

Run 进入终态后 30 秒内必须生成可查看的完整报告；报告可以从持久化结构化事件重新构建，重建不得改变 Run、Step、Attempt、断言或制品事实，也不得重复计数。

首期趋势统计至少支持按测试项目、Scenario、耗时、通过率和时间范围查询。Scenario 执行通过率固定为 `passed / (passed + failed)`；`rejected`、`cancelled`、`queued` 和 `running` 不进入分母，拒绝率和取消率必须作为独立指标展示。Suite 同时展示整体 Run 与成员 Scenario 通过率，ApiCheckSet 同时展示集合与变体通过率，聚合结果不得覆盖成员事实。趋势样本的删除必须随保留期限一并执行。

## 10. 通知

- 通知模型应可扩展。
- 首期支持 Web 站内通知与钉钉；邮件和企业微信后续接入。
- 钉钉通知渠道是测试项目下的受管配置实体，至少包含稳定 `channelRef`、显示名称、加密保存的机器人 Webhook 与签名密钥，以及固定群组/@人设置。只有拥有 `manage_notification_channel` 的用户可以创建、修改、测试或停用渠道，关键操作必须审计。
- 站内通知接收人使用稳定平台用户 ID；钉钉通知的接收边界由所选项目 `channelRef` 及其固定群组/@人设置决定。一个项目可以配置多个渠道，例如测试群、研发群和失败告警群。
- 定时任务可配置 `passed`、`failed`、`rejected` 三类 Run 终态事件与已有接收人/渠道；手动运行可临时选择已配置的平台用户或项目通知渠道，但不能输入临时 Webhook、签名密钥、手机号或钉钉用户标识。P0 不提供任意事件表达式。
- 运行快照固化所选 `channelRef`、渠道配置版本、接收人与通知策略，但不保存 Webhook 或签名密钥明文。
- 修改通知渠道会产生新的不可变配置版本；已经形成快照的 Run 继续引用原版本，不自动改发新渠道。普通密钥轮换允许仍引用旧版本的已冻结通知完成投递，旧密钥材料至少保留到不存在待投递或重试事件；失败时只记录通知失败。
- 紧急停用通知渠道覆盖其全部历史版本，尚未发送或正在重试的通知立即停止并记录 `NOTIFICATION_CHANNEL_DISABLED`；不得自动改发其他渠道，也不得改变 Run 结果。被运行快照或通知事件引用的渠道和版本在 P0 只能停用，不能永久删除。
- 通知只包含状态、耗时、摘要和报告链接，不得包含原始数据或凭据。
- 每个通知事件具有稳定 `eventId`，渠道 Adapter 必须据此去重。首次投递失败后最多重试三次并记录每次尝试；重试采用平台版本化的有界退避策略，不由 YAML 或单次运行任意修改。
- 通知投递失败不得改变 Run 结果。重试耗尽后记录结构化通知失败事件，并在站内向有权查看该任务的用户提示；钉钉或站内通知故障不能被误报为测试执行失败。

## 11. P0 部署与恢复基线

- P0 面向单组织内部私有部署，不承诺控制面主动高可用、自动故障切换或跨机房容灾；这些能力后续依据实际可用性要求独立设计和验收。
- P0 提供显式全局传输安全模式 `internal_http` 与 `https_required`。`internal_http` 只允许部署在受防火墙或 VPN 限制的公司内网，不得监听或映射到公网可达入口；平台启动和管理界面必须明确显示当前模式，但不得把 HTTP 描述为与 HTTPS 等价。跨公网、跨不可信网络或扩大到公司内网之外使用前必须切换为 `https_required`。
- 平台外部基础地址必须由部署配置提供，代码、报告链接、站内通知、钉钉通知和回调地址不得写死 `http://`。平台必须支持由受信任反向代理终止 TLS，并且只接受来自部署配置中可信代理的转发协议、主机和客户端地址信息，不能无条件信任任意 `X-Forwarded-*` 请求头。
- HTTP 模式下平台会话 Cookie 仍必须使用 `HttpOnly` 和适当的 `SameSite`；切换到 `https_required` 后必须同时启用 `Secure`，任何 HTTPS 页面不得降级发送不安全 Cookie。平台 Token、会话标识、密码和 raw 数据不得持久化到浏览器 `localStorage`。前端资源、API、WebSocket 和报告链接必须使用相对地址或根据受信任外部基础地址生成，使 HTTPS 切换不需要修改业务代码或迁移数据。
- P0 不强制内部 CA、云证书服务或组件间 mTLS。同机且仅绑定回环地址的组件可以使用 HTTP；跨主机组件仍必须具备独立服务身份认证，并为后续 TLS 保留可配置端点与证书挂载位置。明文健康检查只能位于受控内部网络并返回非敏感状态。
- 部署管理员通过一次性注册 Token 接纳 Worker；Token 首次成功使用或到期后立即失效。每个 Worker 注册后获得唯一、可轮换、可撤销的服务身份与凭据，禁止在镜像、代码或多个 Worker 间共享全局固定 Token。
- Worker 服务身份只允许声明能力、领取分配给自身的任务、读取当前任务必需的最小快照/凭据材料并上报结构化事件或制品，不得访问平台用户、角色、授权和普通配置管理接口。注册、凭据轮换、撤销、能力变化和任务领取必须审计。
- Worker 被禁用或服务凭据被撤销后不得领取新任务；正在执行的 Run 按 Worker 失联和平台故障规则结束，不因身份撤销自动重放。后续引入 mTLS 时将同一 Worker 身份绑定客户端证书，不改变任务与事件协议。
- 部署级出站网络策略必须将平台组件依赖通道与测试执行出站通道分别配置。测试项目可以在部署策略允许范围内按资源类型、域名、CIDR 和端口进一步收紧，但不能自行扩大；API、Browser、Git、SQL、认证 Redis 和通知 Adapter 使用相应资源类型规则，不得用一种连接类型绕过另一种规则。
- Target System、Managed Connection 和通知渠道默认不得指向 TestPlat 自身的平台数据库、会话/队列 Redis、对象存储管理接口或 Control 管理接口。云实例元数据地址及部署策略列出的基础设施地址默认拒绝。域名在解析后、建立连接前以及 HTTP 重定向到新地址后都必须重新检查实际目标，避免 DNS 或重定向绕过。
- 若确需使用 TestPlat 测试 TestPlat 自身，超管可以创建范围明确的部署级例外，指定资源类型、目标地址、端口和有效期；例外必须展示影响范围、审计创建/修改/使用，并且不能授予浏览器数据库凭据或绕过现有权限、只读、行数、超时和报告规则。P0 不建设独立出站代理，只要求所有 Adapter 在连接发起前调用统一策略检查。
- 平台配置、用户与授权、发布修订、运行快照、队列事实、结构化结果、审计记录和制品元数据必须进入可备份、可恢复的持久存储。备份中的敏感配置和凭据继续加密，并遵守既定保留与删除期限。
- P0 随部署提供每天一次的自动备份任务和恢复命令，不建设复杂的 Web 备份中心。超管可以在平台整体配置中设置每日执行时间，默认使用平台时区 `Asia/Shanghai` 的 `02:00`；P0 不开放 Cron 表达式、每天多次、按项目备份或差异备份配置。修改时间只影响下一次尚未开始的备份，不补跑已经错过的时点。
- 自动备份采用最近 7 天滚动保留，升级前另行创建的可验证备份同样不得突破既定数据删除边界。备份失败必须记录结构化运维事件并向超管发送站内通知；恢复只能由部署管理员通过受控命令在维护状态下执行，不能从 Web 覆盖正在运行的平台。P0 上线验收必须完成一次隔离环境恢复演练，后续季度演练作为运维建议，不由平台自动调度或作为持续运行前提。
- Worker 可以横向扩展，但不是产品配置或运行事实的权威来源。Worker 故障不得抹去已受理 Run、快照或已持久化时间线；运行中不可恢复的 Worker 故障仍按 `failed + platform` 结束，不自动重放。
- 调度器必须使用可配置的 Worker 能力槽位。P0 参考验收负载至少支持 10 个不含 Browser 的 API/SQL Run 与 3 个包含 Browser 的 Run 同时运行；包含任一 Browser Step 的 Run 按 Browser 能力槽位调度。增加兼容 Worker 后可扩展槽位，不改变资产或运行协议。
- P0 全局最多保存 1000 个 `queued` Run。容量尚未达到上限时，新 Run 继续入队而不因 Worker 繁忙被拒绝；达到上限后，新请求以 `rejected + policy / QUEUE_CAPACITY_EXCEEDED` 结束。P0 不提供项目级并发配额、项目优先级或人工插队。
- 在上述参考负载、控制面及其存储健康且不把外部 Git/被测系统耗时计入平台响应时，常用列表、详情和趋势查询 p95 不超过 2 秒；创建手动 Run、保存平台配置、创建或修改定时任务的 p95 不超过 3 秒。
- Git 同步、全量资产校验、发布和报告生成采用可查询状态的异步任务；控制面请求必须在 3 秒内返回任务 ID，不以长连接等待全部工作完成。列表默认每页 50 条且单页最多 100 条。
- P0 恢复验收基线为 `RPO <= 24 小时`、`RTO <= 4 小时`。必须通过一次从备份恢复到隔离环境的演练证明：恢复点范围可说明，平台能重新读取发布修订和历史运行，未完成运行不会被自动重放。
- P0 升级使用维护窗口，不要求零停机、蓝绿部署或滚动数据库迁移。进入维护模式后，控制面拒绝新手动 Run、Git 同步、资产发布和配置变更；定时触发按停机规则记录为跳过且不补跑。升级前必须等待 `running` Run 自然结束、验证排队快照所需 DSL/协议/Adapter/Worker 能力兼容，并创建可验证的升级前备份；任一条件不满足即阻止升级。P0 不承诺原地数据库降级，失败回退通过恢复升级前备份完成。
- Adapter 只能由部署管理员随平台部署或升级安装，不能由平台用户通过 Web、YAML 或 Git 资产上传、热加载或执行代码。每个 Adapter 必须声明稳定 ID、版本、能力、兼容协议和内容摘要；运行快照固定所需版本，兼容 Worker 缺失时在执行前拒绝。
- P0 只交付黄金流程所需的内置 HTTP、Playwright Chromium、MySQL、Redis 验证码和钉钉 Adapter。第三方插件市场、运行时热加载和用户自定义 Adapter 属于后续独立扩展，不得绕过 Worker 能力声明和版本兼容检查。
- P0 不提供平台配置包的导入或导出，不支持选择性迁移项目、环境、目标系统、受控连接、身份、角色权限、通知渠道或其他平台配置。整个平台的备份恢复只用于同一部署的灾难恢复和升级回退，不构成配置迁移协议，也不能被用于绕过凭据、主密钥或权限边界。

## 12. 后续扩展边界

以下不是首期交付目标，但内核和平台模型必须留出受控扩展点：

- 步骤级条件执行：P1 支持基于后续版本化能力开放的 `ResolvedScenarioInputs` 或先前步骤输出的 `when`；同时定义跳过传播、可选输出、缺失依赖、cleanup 引用和报告状态。首版不支持任意嵌套的 `if` / `else` / `switch`。
- ES 受控检索：后续通过版本化 `es.search` 动作开放，定义连接与索引绑定、结构化查询白名单、有界结果、超时、审计和结果契约；不得开放任意 HTTP、脚本或写操作。
- 测试工具与脚本执行：SQL 测试工具遵守第 4.9 节的独立人工入口；其他工具必须定义语言或操作白名单、隔离、网络/文件权限、超时、审计和制品策略，不能直接暴露宿主机 Shell。
- 自动化流程数据库写操作：必须在 SQL 测试工具和数据库策略基础稳定后，通过已发布 `SqlContract`、独立 `sql.execute` 动作、写凭据、事务与影响行数保护受控开放；不得把 `sql.query` 或测试工具的自由 SQL 入口直接用于定时流程。ES 写入在只读检索之后继续单独评估。
- 简单并发和专项测试：作为独立运行模式，定义并发单位、速率、持续时间、账号/数据隔离、配额、取消、超时、阈值和结果聚合；不能把现有普通 Suite 并发字段当作已实现能力。
- Agent 草稿生成：见第 5.2 节。后续设计需要单独确认支持的接口文档格式与 `curl` 方言、请求/响应示例的选择、认证引用映射、校验变体生成、来源与假设留痕以及人工审阅和发布门禁；P0 不提供任何导入或生成入口。
- MCP：仅在平台 API、鉴权、队列、Worker、报告访问控制成熟后接入。MCP 默认只触发已发布资产、返回异步运行 ID 和脱敏摘要；不得读取凭据，也不得绕过不可逆动作的重放限制。
- XPath 定位：后续通过新 DSL 版本增加独立定位策略、受限语法、唯一匹配和兼容性测试；不得借用 `css` 或改变已发布 PageContract 的解释。
- 图片治理：后续可增加截图区域规则、OCR/像素处理和截图专属访问能力；P0 不提供这些能力，也不宣称原始截图已脱敏。
- 项目永久删除：后续如确有需求，必须独立设计影响范围预览、二次确认、运行与审计保留关系及不可恢复边界；P0 只允许可恢复归档。
- 配置包迁移：后续有实际跨部署复制需求时，再设计版本化配置包、稳定引用映射、依赖与冲突预检、原子导入和回滚；非敏感配置与凭据材料必须分离，凭据只能重新录入或通过专门的加密迁移协议处理。

## 13. 明确不做

- 不改造旧平台，不将旧执行器或旧 DSL 作为新平台运行时依赖。
- 首期不做 Web 资产自由编辑、Git 写回、PR 创建、Agent 自动发布、临时运行参数、自由接口调试台、用户自定义重试、邮件重置密码、邮件/企业微信通知、平台配置包导入导出、通用 Shell 执行或性能压测实现。
- 不将测试数据、环境、被测系统凭据和平台用户权限混合进同一种 YAML 或同一个概念模型。

## 14. 后续设计顺序

1. 基于本需求冻结新 DSL 的最小语法、静态校验边界和跨目标系统引用规则。
2. 设计控制面与执行内核之间的发布修订、运行快照、计划和结果契约。
3. 将已批准的产品目标、PRD、领域术语、DSL、技术架构、跨组件协议、首期资产目录、关键协定、需求追溯矩阵、明确不做项和旧系统参考边界归档为带清单与内容摘要的初始产品基线。
4. 初始产品基线完成并经用户确认后，才制定分阶段实施计划，再按独立模块实现与验收。

实施计划不得成为修改产品需求或公开契约的隐式入口。后续若发现需求、资产语义、认证/安全边界或跨模块协议必须改变，应先评估影响并更新产品基线，经确认后再修订实施计划；不能只在任务拆分或代码中改变早期协定。
