## 2. 产品愿景

建设一个全新的、通用且可长期演进的测试执行平台，使测试人员和测试开发能够用统一、可审查、可版本化的方式定义并运行自动化测试，将跨接口、跨 Web 页面、跨数据源、跨目标系统和跨账号的业务验证流程沉淀为可重复执行的测试资产。

TestPlat 不是对旧平台的改造，也不把旧 DSL、旧执行器或公司专属业务直接搬入新平台。`testplat-new`、`ai-test-platform` 等已有项目只作为能力、交互和风险分析的只读参考来源；经分析确认具有通用价值的能力，需要按照新平台的领域边界和协议重新设计后才能进入 TestPlat。

平台的长期目标是：当使用者更换公司、项目或业务系统时，只需替换测试资产、环境绑定、凭据引用和确有必要的专用 Adapter，不修改通用内核，也不重新设计整套执行体系。

## 3. 建设背景与核心问题

现有自动化测试实践通常散落在脚本、配置文件、接口工具、浏览器工具和公司专属平台中，容易产生以下问题：

1. 一条真实业务流程会跨越多个项目、平台和账号，单一接口工具或单一 UI 工具无法完整表达和验证。
2. 登录方式、会话有效性和账号切换规则与具体系统耦合，迁移到新项目时往往需要修改执行代码。
3. 测试数据、环境配置、凭据和业务流程混在一起，难以复用、审计和安全管理。
4. 运行所使用的资产和配置会持续变化，失败后难以回答“当时到底执行了什么”。
5. 控制台文本不足以还原执行顺序、实际输入、变量变化、请求响应、断言和失败原因，问题定位依赖人工翻查。
6. 旧平台中的有效能力与历史业务耦合并存，直接迁移会把旧边界和技术债一并固化到新平台。

TestPlat 要解决的不是“再做一个脚本入口”，而是建立一套从资产管理、确定性编译、隔离执行到证据留存和趋势分析的完整测试执行闭环。

## 4. 目标用户与核心使用场景

### 4.1 目标用户

- 测试开发：设计和维护可复用的测试契约、流程、数据及扩展能力。
- 测试人员：选择项目、环境和已发布业务场景，执行测试并分析结果。
- 平台超管与管理员：管理平台用户、角色、被测系统身份、凭据、环境、目标系统、受控连接和平台策略。
- 普通用户：P0 可浏览并运行平台内所有测试项目的已发布资产，但只能查看自己的 `masked` 运行结果。
- 只读人员：按角色权限配置查看获权结果和趋势，初始模板不允许触发运行。

首期角色不按测试项目进一步划分数据权限，具备运行能力的全局角色可以访问平台内所有测试项目；结果查看仍按角色能力与本人/全局数据范围控制。角色到功能和数据访问能力的映射必须可由平台配置并审计，不能按角色名称写死在代码中；后续可以在不改变执行内核的前提下扩展项目级授权。

### 4.2 核心使用场景

1. 用户在 Web 中选择测试项目、环境和已发布的业务场景，一键执行跨 API、Browser 和 SQL 只读查询的完整业务链路；ES 受控检索在后续阶段接入。
2. 一个 Scenario 按明确顺序调用多个目标系统，并在不同步骤显式切换被测系统身份；不同系统和通道之间不隐式共享认证状态。
3. 用户运行一个单接口校验资产，对同一接口的多个命名校验变体获得独立、可追踪的结果。
4. 用户把多个业务场景组成有序执行集合，并在创建运行任务时选择失败立即停止或继续执行。
5. 用户创建定时任务；同一任务的前一实例未结束时，后续实例排队等待，且每次触发都使用当时冻结的运行快照。
6. 用户从运行报告和结构化日志中查看整体顺序、步骤时间线、输入、变量、请求响应、断言、截图、制品和失败原因。

## 5. 产品核心闭环

TestPlat 的核心闭环固定为：

```text
版本化 YAML 测试资产
  -> 控制面读取、校验和发布
  -> 形成不可变的已发布修订
  -> 触发运行并冻结运行快照
  -> 独立 Engine 编译确定性执行计划
  -> Worker 按计划执行组合流程
  -> 回传结构化运行事件、结果和制品
  -> 平台保存报告、日志和趋势
  -> 用户定位问题并维护下一版资产
```

控制面负责管理和发布，Engine 负责解释与编译确定性计划，Worker 负责受控执行。三者通过版本化协议协作，不能依赖共享进程内状态或未经声明的隐式上下文。

首期 Git 是 YAML 测试资产的唯一可写权威。平台可以读取、校验、发布和运行资产，但不能在 Web 中直接修改并写回 Git。一次运行只能基于已发布修订和冻结的运行快照，不得在排队或执行过程中读取随后变化的分支、资产或配置。

用户发起运行时只选择一次项目环境，例如 `test`。该环境作为项目级运行上下文，分别解析场景引用的 API/Web 目标系统绑定和 SQL/ES 受控连接绑定；缺少任一必要绑定时必须在进入执行队列前拒绝，不能由 Worker 临时猜测或补全。

## 6. “通用”的判定标准

“通用”不是支持无限配置，而是把稳定内核与可替换业务内容分开。TestPlat 必须同时满足以下条件：

1. **业务无关**：通用内核不包含公司名、项目名、站点地址、登录页面规则、业务字段、固定账号或具体业务流程。
2. **目标可替换**：环境地址、目标系统、受控连接和认证方式通过平台绑定或受控 Adapter 提供，不写死在执行逻辑中。
3. **资产可迁移**：业务流程、接口契约、页面契约和测试数据通过版本化资产表达，并以稳定标识引用，而不是依赖仓库路径或本地文件布局。
4. **能力可组合**：API、Browser、SQL 查询、数据转换和后续扩展动作遵守统一的步骤、输入输出、失败和证据模型；后续 ES 检索复用同一模型扩展。
5. **扩展受约束**：新增协议、动作、认证方式、数据操作符或通知渠道通过明确契约和版本化扩展点接入，不能绕过内核规则。
6. **语义可兼容**：已经发布的资产和协议语义不能因依赖升级或内部重构而静默改变；不兼容变化必须显式升级版本。
7. **专用能力可隔离**：少数项目确实需要的特殊逻辑可以通过受控 Adapter 承载，但 Adapter 不能反向污染公共领域模型或成为普通流程的隐藏依赖。

如果接入新公司或新项目必须修改 Engine 的通用语义、在 Worker 中加入业务判断，或复制一套专用执行链路，均视为未达到“通用”目标。

## 7. 不可变产品原则

### 7.1 资产、发布与执行确定性

- YAML 资产必须版本化、可校验、可发布和可追溯。
- 已发布修订和运行快照必须不可变；相同快照应被编译为语义一致的执行计划。
- 资产中的引用、输入、输出和执行顺序必须显式，不能依赖全局隐式变量、目录扫描结果或运行时猜测。
- 执行状态与失败原因必须分开建模，使结果既能表达生命周期，也能稳定分类和定位失败。

### 7.2 跨系统、跨账号与认证隔离

- 一个测试项目可以管理多个目标系统，一个 Scenario 必须能够跨多个目标系统执行。
- 目标系统承载 API/Web 被测业务应用，受控连接承载 SQL/ES 技术连接；二者是测试项目下的并列配置实体，由同一环境上下文分别解析。
- API 和 Browser 步骤必须显式声明被测系统身份或显式匿名，不继承模糊的默认账号。
- 同一流程可以按步骤切换多个账号；跨目标系统只允许显式传递业务数据，不得共享 Cookie、Token、BrowserContext、认证状态或凭据。
- 平台用户、被测系统身份、凭据、认证规则和运行会话是不同概念，必须独立管理。
- 被测系统凭据由平台加密保存，资产只引用非敏感别名。运行时实际发出的业务请求可以作为加密原始证据保存，并由获权用户查看其中的认证头、Token、Cookie 等真实值；这不允许把明文凭据写入 YAML，也不允许跨通道复用认证状态。

### 7.3 可组合执行与风险控制

- 业务场景能够按确定顺序组合 API、Browser、SQL 只读查询、数据转换和可复用 Flow。
- 步骤产生的动态数据通过具名、类型化、不可变输出传递给后续步骤，不回写静态 DataSet。
- 等待轮询、故障重试、主动重复和整段重跑都可能再次产生外部影响，必须服从统一的重放资格模型。
- 支付、结算、退款、业务写入及其他不可逆动作，在结果不确定且没有明确授权时，默认禁止自动重放。
- 首期 SQL 仅开放受控、参数化、有界的只读能力，不能通过自由脚本绕过权限、审计和风险边界；ES 不属于 P0。

### 7.4 可观察、可审计与可清理

- 每次运行必须形成结构化时间线，能够还原整体运行顺序、步骤和尝试、输入、已解析变量、输出、请求响应、认证状态变化、断言和错误。
- 外部动作执行前必须先持久化尝试事实，结果事实持久化后才能进入下一步骤；平台无法确认已发动作结果时必须停止并保留结果不确定证据，不能自动重放。
- 运行结果必须关联确定的资产修订、运行快照、环境与目标绑定、任务策略和通知配置。
- 报告的结构化运行数据支持可配置的脱敏、授权揭示和原始数据模式，以便在最小暴露与获权排障之间切换；具备 raw 权限的用户可以在线查看实际业务请求响应中的完整值，包括认证头、Token、Cookie、被测系统登录密码、支付密码和验证码。P0 截图不做图片脱敏或专属权限，拥有 Run 查看权限的用户可以查看原始截图；P0 不提供 raw 或截图下载导出。平台自身账号密码、Git 凭据和受控连接凭据不属于业务运行证据，不能混入报告。
- 敏感查看、资产发布、平台配置、权限变更、项目归档恢复和数据清理等关键操作必须形成只追加的审计事件，能回答谁在什么时间对什么对象执行了什么操作以及结果如何；审计不复制业务报文或凭据明文。
- 运行、报告、日志、制品和趋势样本默认保留 30 天、最多 180 天；到期后主存储在 24 小时内删除，备份和异地副本在 7 天内删除，只保留不含业务数据的清理审计事件。P0 不允许任何角色手工删除单个 Run、报告或制品，提前清理只能通过受控调整保留策略完成。

### 7.5 控制面与执行面分离

- Web 控制面不直接承担测试执行，Worker 不承担产品配置和资产发布职责。
- Engine 以版本化契约接收确定输入并生成执行计划，不通过读取控制面数据库的临时状态来补全执行语义。
- 平台新增 Web 交互、外部调用入口或部署方式时，不应改变已发布资产的执行含义。

## 8. 首期产品目标

首期（P0）以内部测试环境为主要使用环境，完成一条真正可使用、可追溯并可正式验收的端到端闭环，而不是一次实现所有远期能力。P0 中列出的能力均为首期发布验收的硬门槛；P1、P2 表示后续阶段，不进入 P0 完成判定。提前实现的后续能力应单独验收，不能替代未完成的 P0 能力。

P0 面向单一组织内部的私有部署，可以由多个团队共同使用并管理多个测试项目，但不承诺租户级隔离。测试项目在 P0 是资产、配置、运行、命名和后续配额的管理边界，不是完整的平台用户数据权限边界；多组织、多租户和项目级细粒度授权属于后续独立演进范围。

### 8.1 首期能力范围

- 提供本地平台账号、自助注册、注册后自动分配普通用户角色、管理员升权/换角色和管理员重置密码，支持超管、管理员、测试人员、普通用户和只读人员五类角色。自助注册不能直接获得管理员或超管能力；普通用户在 P0 可运行所有项目的已发布资产，但只能查看自己的 `masked` 结果。
- 在 Web 中管理测试项目、多个目标系统、测试环境、被测系统身份、加密凭据、认证 Profile、Git 资产源、受控连接和保留策略。
- 从标准 Git URL 手动接入资产源，每次同步固定默认分支 commit；只允许发布平台完整获取并校验通过的已同步提交。资产根目录是文件访问边界，资产不得引用根目录外的文件，P0 不支持 submodule 或 LFS。
- 读取和严格校验 YAML 资产，由拥有发布权限的用户直接发布不可变修订。
- 支持运行已发布的 Scenario、Suite 和 ApiCheckSet；首期只运行 YAML 中已经固定的数据，不在 Web 临时填写或修改运行参数。
- 支持手动运行和定时运行；任务显式保存 IANA 时区，同一定时任务采用 FIFO 串行且最多积压一个待执行实例，错过的触发默认不补跑，并按计划时间幂等去重。
- 平台默认以 `Asia/Shanghai` 中国时区创建和展示时间，同时保存 UTC 时间点与任务显式 IANA 时区；服务器本地时区不能改变调度语义。
- 支持跨目标系统、跨账号的 API 与 Browser 组合流程，并支持 SQL 只读查询、显式数据传递、有限集合执行和受控等待轮询。
- 支持多账号并存、显式切换、会话有效性校验和失效后重新认证；API 与 Browser 会话分别管理，不能相互替代或泄漏认证状态。
- 同一环境、目标系统和执行身份同时只允许一个 Run 使用，跨 API/Browser 通道统一串行；一个 Run 所需的全部身份租约在开始执行前原子获取，需要并行时使用不同的确定性身份槽位，不能让同一测试账号并发运行。
- 排队、动作、等待、Run、cleanup、成员数量、动作实例、SQL 行数及制品大小均受明确 P0 上限约束；超限必须形成可解释失败，不能无限等待、无限执行或静默丢弃证据。
- 执行集合在创建任务或发起运行时可配置失败立即停止或继续执行，该策略进入运行快照。
- 保存总体结果、步骤时间线、请求响应、变量、断言、UI 截图、失败原因和制品，并提供可读的运行日志与报告。
- 提供按测试项目、Scenario、时间范围查看耗时和通过率的基础趋势；执行通过率只统计真正进入执行并以通过或失败结束的 Run，拒绝和取消单独展示。
- 支持 Web 站内通知和钉钉通知。站内通知使用稳定平台用户 ID；钉钉通知只能选择项目下由管理员预先配置的通知渠道，不接收单次运行临时输入的 Webhook。定时任务或手动运行可配置通过、失败、拒绝三类终态事件及已有渠道；通知失败独立记录，不改变 Run 结果。
- P0 不承诺控制面主动高可用或跨机房容灾，但持久状态必须可备份恢复，Worker 可横向扩展；部署提供每天一次、执行时间可配置的自动备份和恢复命令，恢复验收基线为 `RPO <= 24 小时`、`RTO <= 4 小时`。
- P0 通过维护窗口升级，不承诺零停机或滚动数据库迁移。升级前必须停止新运行与配置变更、自然排空正在运行的 Run、校验排队快照兼容性并创建可验证备份；不兼容时阻止升级，回退通过恢复备份完成。
- P0 允许在受控公司内网使用显式 `internal_http` 部署模式，不要求首期建设证书体系，但不得暴露公网；平台从第一天支持可配置外部地址、可信反向代理和 `https_required` 模式，后续启用 HTTPS 不迁移业务数据或改变资产语义。
- 平台自身数据库、会话/队列 Redis 和对象存储等系统依赖，与测试动作访问的业务 Target System 和 Managed Connection 使用不同的网络与凭据边界；Web 可以管理受控业务连接，Worker 可以执行获准访问，但普通测试资产不能借此访问平台内部存储。
- P0 参考验收负载支持 10 个 API/SQL-only Run 与 3 个包含 Browser 的 Run 并发、1000 个 Run 排队；常用查询 p95 不超过 2 秒，普通配置和运行创建 p95 不超过 3 秒，定时任务 99% 在计划时间后 60 秒内创建并冻结快照。
- Adapter 只由部署管理员随平台版本安装并进入 Worker 能力声明，不从 Web、YAML 或业务资产仓库动态加载代码。测试项目 P0 只支持可恢复归档，不支持 Web 永久删除；恢复归档项目不自动重新启用定时任务、恢复已拒绝 Run 或补跑归档期间触发。
- P0 不提供项目、环境、目标系统、连接、身份、权限或通知配置的配置包导入导出；部署级备份恢复不能被当作跨平台选择性迁移配置的功能。

### 8.2 首期完成标准

首期只有在以下结果能够通过真实示例端到端验证时，才视为产品闭环成立：

1. 一份合法资产可以从 Git 被读取、校验、发布，并形成不可变修订。
2. 用户可以在 Web 选择已发布资产和测试环境发起手动或定时运行，运行请求形成不可变快照并进入队列。
3. Engine 能把快照编译为确定性计划，Worker 能按顺序执行跨系统、跨账号的 API 与 Browser 流程，并执行受控 SQL 只读验证。
4. 前置步骤产生的动态结果能够经显式输出和必要的数据转换被后续步骤使用，不依赖隐式共享状态。
5. 成功、断言失败、认证失败、超时、配置拒绝和平台异常都能以统一状态、失败分类和稳定证据呈现。
6. 用户能从报告和日志还原一次运行实际使用的修订、配置、步骤顺序、输入输出、请求响应、断言和失败位置。
7. 报告访问、敏感业务数据展示、凭据隔离、审计与到期删除符合平台策略。
8. 将真实业务资产、环境和凭据替换为另一个项目的内容时，不需要修改通用 Engine 和 Worker 内核。
9. 从备份恢复到隔离环境后，能够说明恢复点、读取发布修订和历史运行，且未完成运行不会被自动重放。
10. 外部动作尝试和结果事件在 Worker 故障或重复投递后仍可幂等还原，Run 终态后 30 秒内可查看完整报告。
11. 审计存储失败时不会向用户返回敏感真实值、提交平台关键变更或让 Worker 使用无记录的凭据执行外部动作。
12. 通知渠道、项目恢复与维护窗口升级分别通过受控渠道、无自动重放和可验证备份的验收。

上述并发、队列、响应、定时、报告和恢复数值是已确认的 P0 产品验收基线。总体技术架构阶段仍需据此确定参考部署的 CPU、内存、存储、网络和 Worker 数量，并形成可重复的测量方法；不得通过降低本目标中的验收数值来掩盖部署规格不足。

## 9. 长期演进方向

以下能力是已确认的演进方向，不是首期交付承诺。首期设计必须保留清晰扩展位置，但不能为尚未实现的能力制造虚假可用入口：

- 从 Git 单一编辑模式演进到 Git 与 Web 协同维护资产，并继续保留修订、审核和发布边界。
- 从接口文档或接口 `curl` 示例中提取信息，由 Agent 生成符合当前 DSL 的 `ApiContract` 与 `ApiCheckSet` 候选 YAML 草稿；草稿必须保留来源和生成假设，经过 Schema、引用、风险校验与人工确认后才能发布，Agent 不自动发布，也不得把输入中的真实凭据写入资产。
- 增加独立测试工具能力，包括受控的 SQL 查询、造数、脚本或数据处理工具；工具入口与自动化流程能力共享基础设施，但必须具备白名单、隔离、权限、超时、审计和制品边界，并遵守不同于自动化流程的风险策略。
- 在只读数据库能力成熟后，通过已发布 SqlContract 和独立写动作受控支持自动化流程中的数据库写操作。
- 增加步骤级条件执行、受控重试、更丰富的数据转换操作符，并通过版本化语义保持旧资产兼容。
- 增加受控 ES 只读检索，沿用受控连接、结构化查询、有界结果、访问策略和审计模型；ES 写入继续单独评估。
- 增加简单并发和专项测试运行模式，独立定义并发、速率、配额、隔离、取消、阈值和结果聚合，不改变普通业务流程的顺序语义。
- 增加邮件和企业微信通知渠道，并扩展更细粒度的平台授权。
- 在平台 API、鉴权、队列、Worker 和报告访问控制成熟后提供 MCP 集成，使开发版本发布后可以触发已发布的主要流程并获取异步结果和脱敏摘要。
- 在测试环境稳定后支持开发环境及更多标准化环境类型。

## 10. 明确非目标

- 不以兼容旧平台全部行为为目标，不把 `testplat-new` 或 `ai-test-platform` 作为新平台运行时依赖。
- 不在通用内核中实现具体公司的业务逻辑、登录页面规则、固定环境配置或测试数据。
- 不把平台建设为允许任意 Python、JavaScript、Shell、SQL 或浏览器脚本直接执行的无约束脚本平台。
- 不把平台用户权限、被测系统账号、凭据、环境配置和业务测试数据合并为同一概念或同一份 YAML。
- 不以首期覆盖性能压测、复杂并发、任意流程分支、自由接口调试、Web 自由编辑或 Agent 自动发布为目标。
- 不以“功能入口存在”作为完成标准；没有确定输入、执行证据、失败模型、安全边界和验收结果的能力不视为完成。

## 11. 产品成功衡量标准

产品是否成功，优先按以下长期结果判断：

- **可迁移性**：更换业务项目时，主要工作是替换资产和配置，而不是修改通用内核。
- **表达能力**：真实的跨系统、跨账号长业务流程能够由可复用资产清晰表达和组合。
- **可重复性**：任意运行都能定位到不可变输入，并可解释其确定的执行顺序和结果。
- **可诊断性**：使用者无需依赖 Worker 控制台或开发人员人工拼接信息，就能从结构化证据定位失败阶段和原因。
- **安全与审计**：凭据不进入资产和结果，敏感业务数据按授权查看并能按策略彻底清理，关键操作可追踪。
- **可演进性**：新增目标系统、认证方式、动作、工具、通知渠道或外部入口时，通过受控扩展完成，不破坏已有资产语义。
- **实际可用性**：测试人员能够从选择项目和场景开始，一次完成运行、查看报告、接收通知和追踪趋势的日常工作。

每个阶段可以为这些方向设定可测量指标，但指标不得以牺牲产品原则或缩减已确认目标为代价。
