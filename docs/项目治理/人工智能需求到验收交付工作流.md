# TestPlat 人工智能需求到验收交付工作流

## 目的

本工作流把 `docs/产品需求/产品总目标.md` 的产品目标持续收敛为可验收的软件。它不继承重置前的设计、代码、任务拆分或治理规则。

## 唯一产品输入

`docs/产品需求/产品总目标.md` 是产品目标的唯一权威来源。只有用户可以改变它；AI 不得因实现便利、旧项目行为或审查建议静默修改目标。

## 角色与权限

- 用户：确认产品目标、架构性取舍、范围变化、不可逆操作和最终验收。
- AI：完成需求分析、设计、任务规划、实现、验证、局部返修、模块审查和交接。
- AI 在已确认设计和模块范围内连续推进，不会为测试失败或局部审查问题反复请求用户确认。

## 状态机

```text
产品目标
  -> 设计审查
  -> 等待用户确认
  -> 初始基线归档与冻结
  -> 总体交付路线
  -> 模块交付
  -> 模块验收
  -> 集成验收
  -> 产品完成
```

## 初始基线归档与冻结

在制定实施计划之前，必须完成一次“初始基线归档”。这一步是设计阶段的强制出口，用来防止后续实现过程中因遗漏早期约定、误解资产边界或重新引入旧平台语义而推倒实施计划。

基线归档至少包含：

- `docs/产品需求/产品总目标.md`：不可随意改变的产品总目标；
- `docs/产品需求/产品需求规格.md`：已确认的产品范围、优先级、约束和验收要求；
- `docs/领域模型/领域术语.md`：已确认的领域术语和概念边界；
- 已批准的 DSL/领域设计文档；
- 已批准的总体技术架构、组件职责和跨组件协议；
- 首期资产类型目录、示例资产和引用规则；
- 已确认的认证、凭据、数据作用域、执行顺序、失败、报告和保留策略；
- 明确不做项、后续扩展位以及旧仓库只读参考边界；
- 从需求条目到设计章节、验收条件和后续工作包的追溯矩阵；
- 基线清单、生成日期、批准状态和各文件内容摘要。

归档要求：

1. 归档内容必须来自已确认的文档和资产，不能把聊天记录作为权威输入。
2. 每份归档文件必须记录相对路径、内容摘要或校验值，避免归档后被无意替换。
3. 旧平台的代码、旧 DSL 和业务资产只记录为只读参考来源及审计结论，不复制为新平台运行时资产。
4. 基线冻结后，实施计划只能引用基线中的目标和契约；发现需求、公开协议、架构边界或安全策略变化时，必须先更新基线并重新确认影响，不能直接在计划中偷偷改语义。
5. 普通措辞修正、链接修正和不改变语义的排版调整可以在原文档修订，但必须保留变更记录；新增或删除能力必须形成新的基线版本。

推荐归档目录：

```text
docs/基线/<日期>-初始产品基线/
  基线清单.md
  产品总目标.md
  产品需求规格.md
  领域术语.md
  领域专用语言设计.md
  技术架构设计.md
  资产目录.md
  协议目录.md
  决策记录.md
  需求追溯矩阵.md
  旧系统参考边界.md
```

基线归档完成后，项目状态才可以从“设计已批准”进入“允许制定实施计划”。

每个模块在内部依次完成契约、实现、专项验证和完整差异检查。模块达到验收出口后才进行一次独立审查。

## 审查返修

- 局部实现、测试或文档遗漏：AI 在同一模块内修复，只重跑失败探针和直接回归，然后关闭该意见。
- 涉及产品目标、公开契约、架构边界、安全、数据迁移或跨仓协议：AI 停止该模块，说明影响、备选方案和建议，等待用户确认后更新设计。
- 审查意见必须说明违反的验收条件、修改范围和复验方式；否则不能无限扩大返工范围。

## 最小记录

AI 只创建完成当前阶段所需的记录：已确认设计决定、当前交付路线、模块验收证据和交接状态。中间失败、重复尝试和失效方案不写入产品事实记录。

## 目录边界

- `testplat-control/`：控制面仓库。
- `testplat-engine/`：执行面仓库。
- `docs/产品需求/`、`docs/领域模型/`、`docs/设计/` 与 `docs/项目治理/` 中的跨仓文档作为控制面和执行面的共同权威输入；仓库专属实现文档仍由各子仓库维护。
