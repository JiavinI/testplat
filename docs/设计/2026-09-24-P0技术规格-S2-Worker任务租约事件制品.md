# S2：Worker 领取、租约围栏、attempt、事件与制品

状态：已批准。

批准记录：用户于 2026-09-24 确认本规格整体批准；第 9 节技术契约决定属于本次批准范围。

## 1. 权威来源

- 《2026-09-23-总体技术架构与跨组件协议》§§2-3.7、尤其是 Worker 主动领取、租约、事件顺序、制品事务确认、失联围栏和迟到证据。
- 《产品需求规格》§§6.1-6.5、§§9、§§11。
- 《2026-09-21-最小领域专用语言设计》§§12-14。
- `docs/领域模型/领域术语.md` 中“身份租约”“Worker 服务身份”“步骤输出”“生命周期状态”“失败分类”等定义。
- 相关 ADR：0007、0016、0020、0021、0032、0033。

## 2. 依赖与职责

Control 是 Run、队列、租约、顺序号、事件、制品元数据和失败状态权威；Worker 只持有自身租约下当前任务所需的最小材料。Worker 不访问 PostgreSQL、Redis 或 ArtifactStore 文件目录，所有操作经 Control 版本化授权接口。

```text
Worker capability/identity
  -> claim compatible queued task
  -> lease + fence token
  -> fetch snapshot/plan/minimal action material
  -> persist action intent (attemptId + frozen input digest + started)
  -> external action
  -> persist result/event and artifact references
  -> next Step only after result confirmation
```

本链路禁止把“租约重投”解释为“Run 重放”。租约失效后原 Run 封闭，迟到 Worker 只能提交受控补充证据，不能继续外部动作或改写终态。

## 3. 任务领取与租约接口

接口的逻辑操作、授权与状态语义在本规格中冻结；具体 HTTP 路径由后续共享契约 Schema 表达，不得改变这些语义。

### 3.1 Claim

`Worker -> Control: ClaimTask`

请求最小字段：

| 字段 | 约束 |
| --- | --- |
| `workerId` | 从独立服务身份解析，不信任请求体冒认。 |
| `protocolVersion` | 与 Control 主版本及次版本兼容。 |
| `capabilitySet` | DSL、操作符、Adapter/协议版本、Browser/SQL/API 槽位和可用并发槽位；必须与注册时声明一致或经重新声明审计。 |
| `claimRequestId` | 防止网络重试造成同一 Worker 重复领取。 |
| `requestedSlots` | 仅用于声明可用槽位，不得请求突破平台或快照限制。 |

Control 在一个数据库事务内按队列顺序选择：Run 为 `queued`、编译和能力检查已通过、项目未归档/维护阻止、全部身份租约可按 FIFO 原子获取、且任务所需槽位与 Worker 能力兼容。任务领取响应至少包含：`taskRef`、`runId`、`snapshotRef/digest`、`planRef/digest`、`leaseRef`、`fenceToken`、`leaseExpiresAt`、`heartbeatDeadline`、`taskMaterialDigest` 和本次最小能力材料范围。

无可领取任务必须返回空结果而非错误；Worker 撤销、禁用或能力不兼容不得领取新任务。Worker 不得通过 claim 指定任意 `runId` 绕过队列。

### 3.2 Lease 与 Fence

- `leaseRef` 是一次领取事实；`fenceToken` 单调变化且只对当前租约有效。所有 heartbeat、材料读取、事件和制品操作必须携带它，由 Control 原子校验。
- 租约过期由 Control/PostgreSQL 服务端时间判定，不信任 Worker 时钟。P0 初始候选值为租约 30 秒、每 10 秒 heartbeat、无隐藏宽限期；最终数值须经故障 prototype 校准并写入部署级契约参数。
- 租约续租只允许当前 Worker、当前 `taskRef` 和当前 `fenceToken`；不得由另一个 Worker 接管同一 Run。
- Control 发现心跳超时或 Worker 服务身份撤销时，必须先在同一事务中封闭租约并终结运行：已有 `started` 且结果不确定时为 `failed + platform / ACTION_OUTCOME_UNKNOWN`；尚未开始外部动作时为 `failed + platform / WORKER_LEASE_LOST_BEFORE_ACTION`，均不得重新入队。
- 已经封闭的 `fenceToken` 的所有后续动作请求返回围栏错误；迟到事件保存为 `lateSupplemental`，沿用 Run 证据保留期，仅对具备 raw/运维权限的用户可见，不进入正常事件顺序、报告结果或趋势统计，不能取得新的 Step、Attempt 或结果状态。
- 身份租约和 Worker 槽位在 Run 终态后释放；释放操作幂等。Run 终态由 Control 决定，不由 Worker 自报覆盖。

### 3.3 Material fetch

Worker 只能按当前 `taskRef + fenceToken + runId` 读取。任务领取后可以取得对应 Snapshot 和完整不可变 Plan；环境绑定、凭据、会话及其他敏感动作材料必须按当前 Step/Attempt 最小发放。Control 在返回敏感材料前必须审计使用并检查紧急撤销；Worker 只在内存保留必要时长。Snapshot、Plan、普通日志、错误和制品元数据不得含凭据明文。

## 4. Attempt、Step 和 Run 状态

### 4.1 Attempt 语义

- `attemptId` 是一次具体外部动作尝试的稳定标识，覆盖 API 请求、SQL 查询或 Browser 动作；它不是 Worker 任务重试 ID，也不是 Run ID。
- 每次首次动作、被明确授权的 `wait` 重复和符合双重授权的 `authRefresh` 重复都生成新的 `attemptId`，并在事件中关联同一 Step、`replayKind` 和冻结输入摘要。P0 没有网络故障自动重试、整段 Run 重放或租约重投。
- 在外部副作用之前，Worker 必须先提交 `attempt.started`：目标、动作类型、目标绑定版本、冻结输入摘要、幂等键（若资产提供）和开始时间。Control 未确认该事实时 Worker 不得发送请求、执行 SQL 或操作 Browser。
- 动作完成后必须先提交 `attempt.result`（`passed`、明确失败或 `unknown`）并得到持久化确认，才能进入下一 Step。结果不确定时立即封闭 Run，禁止自动重放和全部资产 cleanup。

### 4.2 状态约束

Run：`queued -> running -> passed|failed|cancelled`，或在未运行前 `queued -> rejected`；P0 不提供取消入口但保留协议状态。Step：`pending -> running -> passed|failed|skipped|cancelled`。状态与失败原因分离；错误至少带 `category`、`code`、`message`、阶段和关联 Step/Attempt。

Control 必须拒绝越级/回退状态转移。主步骤失败仍独立记录 cleanup；主步骤通过但 cleanup 失败，整体 Run 为 `failed`。`ACTION_OUTCOME_UNKNOWN` 后每个未执行 cleanup 都记录 `skipped + OUTCOME_UNKNOWN`，只执行 BrowserContext 销毁、租约释放等平台资源清理。

## 5. 事件协议与幂等确认

### 5.1 Event envelope

```json
{
  "eventId": "<stable-id>",
  "eventType": "attempt.started",
  "runId": "<run-id>",
  "taskRef": "<task-ref>",
  "leaseRef": "<lease-ref>",
  "fenceToken": "<current-token>",
  "stepRef": "<step-ref>",
  "attemptId": "<attempt-id>",
  "producerSequence": 0,
  "occurredAt": "<worker-time>",
  "payloadDigest": "sha256:<digest>",
  "payload": {}
}
```

`payload` 只放结构化、脱敏后可持久化事实；原始请求/响应和截图通过 ArtifactStore 流程关联，不把大正文塞进事件表。

### 5.2 幂等与顺序

- 同一 `eventId`、同一 `payloadDigest` 和相同 envelope 语义重复提交，返回原确认，不重复计数或重复状态转移。
- 同一 `eventId` 携带不同内容，或当前状态不允许该事件，返回协议冲突并写入审计/平台故障事件；不得采用“最后一次”。
- Worker 允许至少一次投递并在网络失败后重投；重投只确认既有事实，不重做外部动作。
- Worker 为当前任务提交从约定起点连续递增的 `producerSequence`；Control 校验成功后分配持久化的 Run canonical `sequence`。发现缺口或倒序时返回 `409` 和 `expectedSequence`，不缓存乱序事件；跨 Step 越权同样拒绝，不能静默排序。
- 事件确认响应至少包含 `eventId`、Control 顺序号、确认时间、结果状态和是否为原确认；Worker 只有拿到确认才推进动作状态。

## 6. 制品上传与关联

### 6.1 两阶段制品流程

1. Worker 向 Control 申请当前 Run/Attempt 范围内的上传流，声明 `artifactKind`、媒体类型、大小上限和预期 SHA-256；Control 校验权限、配额、阶段和围栏。
2. P0 由 Control 流式代理写入 ArtifactStore 暂存对象，Worker 不直接访问制品目录，对象不可被公开 URL 直接访问。未来 OSS/S3 Adapter 可以在相同外部协议下使用短期一次性上传凭证。
3. Worker 提交 finalize，Control/ArtifactStore 校验实际大小和摘要；不匹配、超限或租约失效都不确认。
4. Control 在一个持久事务中写入不可变 `artifactRef` 元数据及引用该制品的结果事件/断言事实；事务成功后才向 Worker 返回可推进的确认。

`artifactRef` 至少关联 `runId`、`stepRef`、`attemptId`、制品类型、摘要、大小、加密/脱敏策略版本和对象状态。ArtifactStore 故障或数据库事务失败不得让 Worker 把 Step 判为已完成；暂存孤儿由定期清理任务按保留期清理，并记录清理事实。

### 6.2 配额与损坏

单制品 50 MiB、单 Run 累计 500 MiB；超限分别以 `failed + action / PAYLOAD_SIZE_LIMIT_EXCEEDED` 和 `failed + policy / RUN_ARTIFACT_QUOTA_EXCEEDED` 结束，不静默丢弃证据。恢复时若数据库有引用但对象缺失，报告必须标记证据损坏，不伪造完整报告。

## 7. 异常路径

- Claim/heartbeat 前 Control 不可用：Worker 不执行外部动作；恢复后不得自动重派原 Run。
- `attempt.started` 持久化失败：不发送动作；Run 可保持/转为平台拒绝，错误不得伪装成业务失败。
- started 已确认，Worker 崩溃、网络分区、结果提交超时或租约到期：`ACTION_OUTCOME_UNKNOWN`，封闭 Run、跳过资产 cleanup。
- 明确结果已确认但 Worker 未收到响应：重投同一 event；不得生成新 attempt。
- 事件顺序冲突、重复 ID 异内容、跨任务围栏 Token：拒绝并记录协议故障。
- ArtifactStore 暂存成功但 finalize/事务失败：不确认结果，保留可审计孤儿清理线索；若外部动作结果未知，遵守 unknown 规则。
- 迟到 Worker 事件只能保存为 `lateSupplemental`；不得刷新 Run 终态、重新持有身份租约、触发下一 Step 或进入趋势统计。

## 8. 验收方法

- 两个 Worker 并发 claim 同一队列：只有一个获得租约；另一个只能领取其他兼容任务。
- 重复 heartbeat、重复 finalize、重复事件和断网重投均幂等；不同内容复用同一 ID 必须冲突。
- 伪造/过期/旧 `fenceToken` 的 material、event、artifact 请求全部拒绝；迟到事件不会改变终态。
- 在 `attempt.started` 前注入数据库故障，确认没有外部 HTTP、SQL 或 Browser 动作；在 started 后到 result 前杀死 Worker，确认 `ACTION_OUTCOME_UNKNOWN`、不重放、cleanup 跳过。
- 上传错误摘要、超大制品、事务提交失败、对象丢失和孤儿清理均有结构化事实，报告不重复计数。
- 校验 10 个 API/SQL Run 与 3 个 Browser Run 的槽位调度、全局 1000 queued 容量和 FIFO 身份租约；不同身份不被全局队首阻塞。
- 恢复 Control/Worker 后，已确认事件、Attempt、制品元数据和 Run 状态不丢失；未完成 Run 不自动重放。

## 9. 已确认的技术契约决定与验证项

用户于 2026-09-24 确认：

1. 租约使用 Control/PostgreSQL 服务端时间；初始候选租约 30 秒、每 10 秒 heartbeat、无隐藏宽限期，最终数值经故障 prototype 校准。
2. Worker 提交连续 `producerSequence`，Control 校验后分配 Run canonical `sequence`；缺口返回 `409 + expectedSequence`，不缓存乱序事件。
3. Snapshot 和完整 Plan 按任务租约授权；凭据、会话和敏感动作材料按 Step/Attempt 最小授权。
4. P0 由 Control 流式代理上传制品；未来对象存储可以在不改变外部协议的前提下使用短期一次性凭证。
5. 迟到证据保存为 `lateSupplemental`，沿用 Run 证据保留期，仅对 raw/运维权限可见，不进入结果或趋势，也不要求人工批准后才保存。
6. 动作前租约失效使用 `failed + platform / WORKER_LEASE_LOST_BEFORE_ACTION`；started 后结果不明使用 `failed + platform / ACTION_OUTCOME_UNKNOWN`。

故障 prototype 只负责校准租约和 heartbeat 数值，并验证在目标参考负载下不会误判健康 Worker；不得改变 Control 的时钟权威、围栏、不重派和结果不确定处理规则。
