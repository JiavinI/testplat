## 2. 已确定边界（不再访谈）

- Control 管理平台配置、Git 同步/校验/整根发布、运行编排和结果访问；独立 Engine 解释并编译确定性计划；Worker 受控执行。三者通过版本化协议协作，不共享隐式进程状态。平台 Git 只读，已发布修订的内容和摘要不可变；活动修订切换不影响已有 Run。
- `ExecutableInvocation` 经输入绑定形成 `Run Snapshot`；P0 的 Scenario 外部输入为空。快照固定修订、绑定、版本、身份解析和策略，但不存凭据明文；紧急撤销可覆盖旧版本引用。Compiler 枚举全部身份租约键，在运行前原子获取。
- Target System 与 Managed Connection 是项目下并列实体；Environment 分别解析其绑定。平台系统依赖与测试出站分离。`actorRef` 是逻辑身份槽位，不是账号池选择器；`pageRef` 是静态契约，`pageHandle` 是不可持久恢复的运行时能力。
- 外部动作之前必须持久化 `attemptId`、冻结输入摘要和 started 事实；事件至少一次投递并按稳定 `eventId` 去重。结果不确定时禁止自动重放和全部资产 cleanup，只做平台资源清理。Worker 失联不重放原 Run。
- 固定角色加可配置能力映射、Web 不透明会话、Worker 独立服务身份、加密原始证据、失败关闭审计、受限出站、部署安装 Adapter、维护排空升级及备份恢复指标均沿用 PRD/ADR，不在此改写。

## 3. 模块及数据流

Control 的运行协调模块持有持久 Run 生命周期、调度、身份租约、事件接收与报告读模型；Engine 的编译模块只接收冻结输入并产出可校验的确定性计划；Worker 的执行模块只按计划及其授权材料运行，通过执行 Adapter 隔离 HTTP、Browser、MySQL 和认证通道。Engine 与 Worker 的接口暴露少量版本化操作及完整的错误、顺序和能力约束，复杂编排留在各模块内部。

数据流：Git commit 固定及全根校验 -> 原子发布完整修订 -> 触发调用并做权限/环境/输入检查 -> 冻结快照 -> Engine 编译计划/能力与租约需求 -> 排队及原子获取租约/槽位 -> Worker 预写 attempt 事实后执行 -> 事件与制品持久化 -> 报告投影和获权查询。任何阶段不可回读活动分支或可变配置补全执行语义。具体数据库事务、JSON 字段和容量参数在后续细化，但不得改变这条数据流及其权威归属。

### 3.1 第一轮已确认的架构选择

- Engine 是独立、无状态的版本化发布单元；Worker 不负责补编译。
- Control 在创建可领取 Run 前调用 Engine 完成编译，并持久化不可变快照及计划摘要；编译失败不进入队列。
- P0 采用容器化单机拓扑作为架构基线，当前全部设计、实现和联调先在本地完成，暂不引入 Kubernetes；后续部署到阿里云或拆分多机时只替换部署参数和存储/网络 Adapter。Worker 横向扩展必须继续服从既定能力槽位和协议，不改变运行事实权威。

### 3.2 第二轮已确认的协议方向

- Control 通过内部版本化 HTTP/JSON 请求-响应接口调用 Engine，编译输入以 `snapshotRef + snapshotDigest + compilerContractVersion` 绑定冻结快照；结果以计划引用、摘要、能力需求及编译版本表达。具体正文归属、鉴权、时限和响应字段仍待细化。
- Worker 以独立服务身份主动向 Control 领取与其声明能力相容的任务，通过有期限的任务租约及心跳续租；Control 持有队列、租约和运行状态权威，租约失效不得自动重投原 Run。
- Snapshot 与 Plan 以不可变内容及 SHA-256 摘要验证；跨组件协商协议主版本与有限兼容次版本、DSL/操作符及 Adapter 能力，未知必需语义拒绝，不静默降级。具体字段兼容矩阵仍待细化。

### 3.3 第三轮已确认的协议方向

- 编译使用有界同步受理预算；超时或 Engine 不可用时记录 `rejected + platform`，不入队。手动 Run 创建的 p95 不超过 3 秒仍是产品验收目标；预算数值和可达性需要在参考部署上验证，不以草案推断替代实测。
- Engine 返回计划正文、内容摘要和能力清单；Control 校验后持久化不可变 Plan 正文，并分配 `planRef`。Worker 只从 Control 按引用领取，Engine 不成为计划存储权威。
- Control 按 `eventId` 幂等接收、按 Run 内序号校验事件顺序。制品先上传并校验大小和摘要，再在同一持久化事务中确认制品元数据及引用它的结果事件；Worker 只有在动作结果事实被持久化确认后才能进入下一 Step。具体上传凭证、孤立暂存对象清理及重投语义尚待细化。

### 3.4 第四轮已确认的协议方向

- 传输、Snapshot/Plan 格式、DSL、操作符和 Adapter 分别校验版本及必要摘要；协议主版本必须相同，次版本只容许已声明的可选扩展，未知必需语义拒绝。升级前逐份检查排队快照兼容性；YAML 对未知字段仍严格拒绝。
- Worker 用稳定 `eventId` 重投未确认事实；Control 为 Run 持久分配顺序号。同一 ID/同一内容返回原确认，同一 ID/不同内容或非法状态转移拒绝并记录协议故障；重投不表示重新执行外部动作。
- Worker 持有有效任务租约、准备执行具体动作时按 `runId + attemptId + 凭据版本引用` 领取当次最小材料；Control 先审计使用并检查紧急撤销，Worker 只在内存保留必要时长。Snapshot、Plan 和普通日志不得含凭据明文。

### 3.5 第五轮已确认的存储方向

- PostgreSQL 是平台配置、发布、Run、队列、身份/任务租约、事件、审计和制品元数据的持久事务权威；它与被测 MySQL Managed Connection 完全隔离。数据库 Schema 和事务细节留待后续设计，但不得产生第二事实来源或改变本文批准的原子性边界。
- 制品通过独立的 `ArtifactStore` 接口保存加密的截图、raw 证据及大制品正文；当前阶段使用本地文件系统目录（开发、本地联调和未来单机部署均可运行），PostgreSQL 只保存元数据、摘要和引用。未来可替换为 OSS/S3/其他对象存储 Adapter，不改变 `artifactRef`、摘要、权限或事件协议；对象不以公开 URL 替代 Control 的权限和审计入口。
- 本地文件系统与数据库同机时只能满足开发和受控内部试运行，不能单独证明备份恢复及异地副本要求。正式 P0 恢复验收前必须配置第二故障域的备份目标（其具体产品/费用另行确认）；在此之前不得宣称已完成 RPO/RTO 验收。
- Redis 只用于可恢复/可重建的辅助用途，不成为 Run、FIFO 租约、任务领取和容量计数的第二事实来源；具体会话和限流实现需服从已批准的即时撤销与安全规则。

### 3.6 第六轮已确认的恢复与报告方向

- 已确认结构化事件及制品元数据是报告/趋势事实源；报告和趋势是可重建投影。终态后异步生成/重试，仍须达到 30 秒可查看的产品验收值；重建不得改写事实或重复计数。
- Control 监测任务租约到期，原子封闭并把执行中的 Run 终结为 `failed + platform`，不重派原 Run。若已有 started 且无确定结果，使用 `ACTION_OUTCOME_UNKNOWN`，跳过全部资产 cleanup；迟到 Worker 不得继续动作或改写终态，但其晚到证据可追加为受控补充记录，不能伪装成原先及时确认的结果。
- `ArtifactStore` 对象先暂存并验证大小/摘要，PostgreSQL 再于同一事务确认制品元数据及引用它的结果事件；未确认的暂存对象定期清理。数据库恢复点和对象清单/摘要组成可验证恢复集，隔离演练验证完整性；缺对象明确标记证据损坏，不伪造完整报告。当前文件系统实现与未来 OSS/S3 实现都必须遵守同一接口。

### 3.7 第七轮已确认的部署与制品调整

- 当前本地开发、联调和协议验证采用容器化单机拓扑，不把 Kubernetes 或托管中间件作为前置条件；后续部署到云服务器时再按实际网络切换 `internal_http`/`https_required`，本地受控联调可使用 `internal_http`。
- 当前制品实现使用本地专用数据卷上的文件系统 `ArtifactStore`，不要求购买 OSS，也不要求引入 MinIO。OSS/S3 等未来实现通过同一 Adapter 接口接入，不改变制品协议、摘要、权限和报告模型。
- 本地数据库、制品目录和备份目标用于开发与受控验证；正式 P0 部署时仍必须配置不同故障域的备份目标并完成恢复演练。这是部署门槛，不是对已批准产品目标的下调。
- 当前定义 `BackupTarget` 接口，先允许本地路径实现用于测试备份/恢复；未来可接入远程文件系统、云厂商快照或 OSS/S3。没有第二故障域时不得宣称已完成正式 RPO/RTO 验收。
- PostgreSQL 数据、制品目录和备份暂存使用不同逻辑卷/挂载点与配额，即使当前都位于本地机器；该布局为后续独立迁移和容量治理保留位置。
- 验收采用协议契约测试、模块测试、故障注入、真实 MySQL/Playwright Chromium/认证 Redis/通知 Adapter 测试，以及目标单机上的并发、报告时限和隔离恢复 prototype。prototype 只使用专用测试环境和可重复数据，不执行真实不可逆业务。
- Worker 不直接访问 PostgreSQL、Redis 或制品文件系统，只通过自身服务身份访问 Control 的任务、快照、按动作凭据和事件接口；Engine 同样通过授权接口读取快照并提交计划。这样保持平台数据面集中，未来替换制品后端时不改变 Worker/Engine 协议。
- 主密钥推荐通过部署系统的只读 Secret 文件挂载提供；“环境变量”只有在由独立 Secret 管理器运行时注入、且不进入 Git/镜像/普通配置/数据库并有泄露控制时才可作为等价实现。普通 `.env` 或 Compose 配置文件不属于该实现。

### 3.8 第七轮已确认的组件边界与密钥方案

- Worker 和 Engine 不直接访问 PostgreSQL、Redis 或制品目录，只经 Control 的版本化授权接口交互；Worker 的任务、快照、凭据、事件和制品权限均按服务身份及当前任务收紧。
- 主密钥默认用 Docker Compose Secret 文件挂载，由部署系统独立提供；受控 Secret 管理器的运行时注入可作为等价 Adapter，但普通 `.env`、镜像、数据库和日志均禁止承载主密钥。
