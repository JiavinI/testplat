# P0 关键协定

状态：初始产品基线派生索引；已随基线于 2026-09-24 确认。

本索引汇总实施计划和代码不得静默改变的核心协定。完整语义以源文件与 38 份 ADR 为准。

## 1. 权威与发布

1. Git 是 P0 YAML 唯一可写权威；Control 只读同步，固定默认分支 commit，完整获取并校验整个资产根。
2. 发布者只能从平台仍保存且校验通过的已同步提交发布整个资产根；不接受任意 SHA、单资产发布、submodule 或 LFS。
3. Published Revision 内容、commit、manifest、摘要和验证结果不可变；活动修订切换只影响后续新 Run。
4. 平台配置实体使用不可变版本和 `expectedVersion` 乐观并发控制，禁止静默最后写入覆盖。

## 2. 调用、快照与编译

1. 所有运行入口统一形成 `ExecutableInvocation -> InputBinder -> Run Snapshot`；P0 外部 Scenario 输入固定为空。
2. Snapshot 固定发布修订、DSL/操作符、环境绑定、Adapter/Worker 能力、身份/Profile/凭据版本引用、策略、报告和通知版本，但不含凭据明文。
3. Snapshot 保存不可变发布对象引用及 closure manifest/摘要，被引用对象与 Snapshot 共同保留和恢复；缺失不能回读 Git 补全。
4. Engine 独立、无状态；Control 在入队前同步有界编译并持久化完整不可变 Plan。编译失败/超时不入队。
5. JSON 摘要使用 RFC 8785 JCS + SHA-256；实体引用使用 UUIDv7 不透明 ID；协议版本使用整数 `major.minor` 和 required/optional features。

## 3. Worker、租约与外部动作

1. Worker 使用唯一、可轮换、可撤销服务身份，主动领取兼容任务；Control 是队列、租约和运行状态权威。
2. Worker 取得完整 Snapshot/Plan，凭据、会话和敏感动作材料按 Step/Attempt 最小发放；Worker 不直接访问平台数据库、Redis 或制品目录。
3. P0 对 `environment + targetRef + actorRef` 使用排他身份租约；一个 Run 所需租约按键 FIFO 一次性原子获取，不部分占有、不运行时追加。
4. 租约以 Control/PostgreSQL 时间为准；Worker 提交连续 `producerSequence`，Control 分配 Run canonical sequence；旧 fence 的所有写入拒绝。
5. 每次外部动作前必须先持久化稳定 `attemptId`、目标、冻结输入摘要和 started 事实；结果确认前不得进入下一 Step。
6. Worker 失联不得自动重派原 Run。动作前失联为 `WORKER_LEASE_LOST_BEFORE_ACTION`；started 后结果不明为 `ACTION_OUTCOME_UNKNOWN`。
7. `ACTION_OUTCOME_UNKNOWN` 跳过全部资产 cleanup，不自动查询、取消、退款、补偿或回滚，只做平台资源清理。

## 4. 事件、制品与报告

1. Worker 事件至少一次投递，按稳定 `eventId` 和 payload 摘要幂等；同 ID 异内容和非法状态转移拒绝。
2. P0 由 Control 流式代理上传制品，验证大小和 SHA-256 后，在同一持久化事务中确认元数据及结果事件引用。
3. 迟到 Worker 证据保存为 `lateSupplemental`，只对 raw/运维权限可见，不改变终态、报告结果或趋势。
4. 结构化事件和制品元数据是报告事实源；报告/趋势是可重建投影，不得改写或重复计算事实。

## 5. 状态、失败和聚合

1. Run 状态封闭为 `queued`、`running`、`passed`、`failed`、`cancelled`、`rejected`；Step 状态封闭为 `pending`、`running`、`passed`、`failed`、`skipped`、`cancelled`。
2. 生命周期状态与失败分类分离。接口错误使用稳定 `code + stage`；只有形成 Run/Step 事实时映射 PRD 十类 `failureCategory`。
3. 主步骤通过但任一 cleanup 失败，Scenario 仍为 failed；Suite/ApiCheckSet 任一成员失败使聚合失败，同时保留成员事实。
4. 平台故障、Worker 失联、超时和策略拒绝不得伪装成 cancelled；恢复后不自动重放。

## 6. 权限、安全与审计

1. 角色是初始模板，代码按稳定 capability 判定；P0 增加 `create_run`、`view_run_summary`、`view_masked_run_data`、`view_trend`、`manage_project_config`、`manage_schedule`。
2. 未认证返回 401；已认证但无权知道敏感对象是否存在时返回 404；对象可见但缺少操作能力返回 403。
3. Web 使用服务端不透明会话、CSRF 和可信 Origin；高影响管理操作要求最近 15 分钟密码认证。
4. raw/revealable、凭据、发布、授权和高敏感配置变更审计失败关闭；普通 masked 查询不依赖逐次敏感审计。
5. 凭据和 raw 证据使用信封加密；主密钥由部署系统独立提供，缺失所需版本时平台失败关闭。
6. 平台依赖通道与测试出站分离；项目只能收紧部署策略，基础设施和元数据地址默认拒绝。

## 7. 部署、恢复与演进

1. P0 以容器化单机为参考架构，先保证可恢复，不承诺主动高可用或 Kubernetes。
2. PostgreSQL 是平台持久事务权威；ArtifactStore 保存大制品正文；Redis 只承担可重建辅助用途。
3. 每日一次备份、保留最近 7 天，正式验收需要第二故障域目标和隔离恢复演练；基线为 RPO 不超过 24 小时、RTO 不超过 4 小时。
4. 升级采用维护排空窗口；不兼容的排队 Snapshot 或不可验证备份会阻止升级。
5. 父仓库 `contracts/` 是跨仓 Schema、fixtures、错误码和兼容矩阵的单一权威；组件仓库不得各自复制协议。
